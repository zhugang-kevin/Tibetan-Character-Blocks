## ⚠️ 一、先更正我 D84 的一处错误

**我当时说：「微信对小游戏内购抽成约 50%，收入测算要对半重算。」**

**这句话不适用于我们。** 原因：
- 那个 50% 是**小游戏 IAP** 的口径，而且来自律所人士的概括；
- 而**小程序虚拟支付**（我们该用的那条路）费率完全不同。

### 真实费率（虚拟支付技术服务费，按「类目 + 设备」区分）

| 端 | 标准费率 | **当前生效费率** |
|---|---|---|
| 安卓 / 鸿蒙 / Windows | 10% | **1%（限时优惠）** |
| **iOS** | 17%（含 12% Apple 佣金） | **12%**（腾讯的 5% 技术服务费当前限时减免） |

**这意味着：B 付 1 元 → 安卓你到手约 0.99 元、iOS 约 0.88 元。**
**打赏模式的商业账完全成立**（D84 里「对半砍」的悲观结论**作废**）。

> 出处：微信开放社区《小程序虚拟支付接入指引》/《小程序虚拟支付技术服务费明细》
> ⚠️ 1% 是**限时优惠**，标准是 10%。需持续关注官方公告。

## ✅ 二、第二处更正：iOS 已经开放了

**我 D84 说「iOS 小程序禁止虚拟支付」—— 那个限制已经是历史。**

| 时间 | 事件 |
|---|---|
| 2018-05-08 ~ 2025-11 | iOS 端**禁止**小程序虚拟支付（长达 7 年半） |
| 2025-11 | 苹果推出「小程序合作伙伴计划」，抽成 30% → **15%**；**微信官方公告：小程序现已全面支持 iOS 端虚拟支付** |
| **2026-04-01 起** | **强制**：小程序内销售虚拟商品**必须全终端接入官方虚拟支付**（`wx.requestVirtualPayment`），**不得**再用普通微信支付卖虚拟商品，也不得引导跳转到 App/公众号/H5 支付。**违规会风险提示、限制功能直至终止服务** |

**对你的意义**：iOS 用户现在也能打赏了，覆盖率从「只有安卓」变成 **全端**。

> ⚠️ **另一面**：2026-04-01 之后，**如果你在小程序里卖任何虚拟商品（含打赏），必须走虚拟支付**。
> 这既是约束也是保护 —— 它意味着这条变现路径是**官方认可的正路**。

## 🧱 五、技术链路（**这里有一处与现行约定冲突，需要你决策**）

### 打赏的完整流程

```
B 点击「送一盏酥油灯 ¥1」
   ↓
小程序 wx.login 拿 code
   ↓
请求【你的服务端】下单
   ↓
服务端：code2Session 换 openid+session_key → 组 signData → 算 paySig + signature
   ↓
小程序 wx.requestVirtualPayment（用服务端返回的签名）
   ↓
用户付款
   ↓
【微信回调你的服务端】→ 校验 → 给 A 记激励 → 返回成功
   ↓
A 收到（游戏内激励 + 订阅消息通知）
```

### 🔴 硬约束：**必须有服务端**

官方核心原则（原话）：
> 「**签名只能在服务端计算**（AppKey 和 session_key **绝不能**出现在小程序前端代码里）」

**而本项目现行约定是 D3：纯本地、无云函数、无后端。**

**这意味着要实现打赏，必须引入服务端。** 这是一个**架构级决策**，也是打赏落地前唯一的拦路石。

**可选方案**：
| 方案 | 说明 |
|---|---|
| **微信云开发（云函数）** | 最省事：官方云函数 + 云数据库，签名放云函数里；**但违反 D3** |
| 自建服务端 | 一台小服务器（¥几十/月）跑 Node，签名+回调+订单表 |
| 第三方 BaaS | 类似云开发但可换供应商 |

**注意**：虚拟支付的「发货回调」需要一个 **HTTPS 公网地址**，所以**无论如何都需要一个服务端**。
