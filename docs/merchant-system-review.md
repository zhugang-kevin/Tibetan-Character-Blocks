## 1. 阻断级问题（3 项，必须先改）

### 🔴 P0-1 「微信支付商品券核销组件」在本项目无法使用

**你的原文（3.2）**：「推荐方案：使用微信支付商品券核销组件……开发者可通过调用 `wx.openBusinessView` 方式在商户小程序中打开核销组件」

**官方事实**（微信支付《小程序核销组件开发指引》，`pay.weixin.qq.com/doc/brand/4016105616`）：

- 组件 `businessType` 固定为 `wxpayCouponUse`，`extraData` 必填 `couponCode`（券唯一标识）+ `stockId`（批次号）+ `authState`。
- 它要解决的问题是：**「摇一摇有优惠」场景下**「用户在商家小程序未登录正确领券账号、找不到券」。
- **开通核销组件权限需联系「对接的微信支付行业运营负责人」申请**，且要求微信 ≥ 8.0.30、小程序基础库 ≥ 2.28.1。
- 券必须在**微信支付侧创建**（有 `stock_id` 批次），且只有从**「摇一摇有优惠」会场**跳到商家小程序时才会携带 `couponCode` / `stockId` / `action` 参数。

**为什么我们用不了**：

| 组件要求 | 我们的情况 |
|---|---|
| 券在微信支付侧创建，有 `stock_id` 批次 | 我们打算游戏内自研发券，不在微信支付侧 |
| 发券方 = 商家（其商户号） | 甜茶馆 MVP 阶段不会有商户号与商品券能力 |
| 入口 = 「摇一摇有优惠」会场 | 我们的入口是游戏内通关 |
| 需微信支付行业运营负责人开通权限 | 个体户小项目拿不到 |

**替代方案**：**自研券 + 自研核销**（见 §3）。这也与 [`business-model-v2.md`](business-model-v2.md) §5 的结论一致。

> 顺带说明：另一个 `businessType: 'shopConsumeVoucher'`（`encrypted_codes` 加密券码）是**视频号小店团购券**的核销，同样不适用。

### 🔴 P0-2 「异业联盟积分抵现金」= 变相发行结算积分，必须删

**你的原文（四·三）**：「消费送积分 → 积分抵现金 → **商家收了会员的抵扣积分后，攒到一定数量，可以找平台申请提现，平台按约定比例把积分换成钱给商家**」

**问题**：

1. 平台发行"消费送积分"、并承诺**按约定比例兑付法币**给商家 → 平台在**经手并兑付资金**，与 §2.1 的二清问题同源（无证从事支付结算业务的风险）。
2. 积分与消费挂钩且可变现 → 触及**单用途预付卡 / 通用代币发行**监管口径，税务上"积分兑换视同销售"，需按规定计缴增值税。
3. 平台对积分与资金的规则不得与充值挂钩、不得设置"越多越赚"的诱导机制（微信与监管口径一致）。

**替代方案**：异业联盟**只保留无资金流的互推**——

```
✅ 用户在甜茶馆核销后 → 推送「附近合作唐卡体验馆，凭今日甜茶券享 9 折」
✅ 唐卡馆核销后 → 推送「附近合作民宿，凭今日体验券享首晚 8 折」
❌ 不发积分、不抵扣现金、不兑付
```

互推是纯内容引导，零资金流，风险归零。

### 🔴 P0-3 「商家裂变 + 区域合伙人抽佣」= 多级分销违规

**你的原文（四·三 商家裂变）**：「商家 A 推荐商家 B 入驻，B 完成首月核销后，A 获得 200 元现金奖励」；「区域合伙人……获得该区域所有商家核销佣金的 10% 作为管理费」

**平台规则**（《微信小程序平台运营规范》`developers.weixin.qq.com/miniprogram/product/index.html`）：

- §5.3 **网赚行为**：不得以"利诱其他用户参与、转发、下载"方式获取收益，包括现金 / 积分 / 礼品。
- §5.9 **多级分销经营行为**：不得通过微信小程序实施多级分销、发布分销信息诱导用户添加或分享。
- 行业通行口径：小程序内**仅一级直接推荐**稳妥；**三级及以上分佣直接违规**，会下架、封禁支付能力。
- 法律侧：《禁止传销条例》口径下，**计酬层级 ≥3 层 + 参与人数 ≥30 人**可刑事立案。

「商家推荐商家得现金」+「区域合伙人抽区域佣金」叠加，容易构成多层计酬。

**替代方案**：

| 保留 | 禁止 |
|---|---|
| 商家介绍费、区域合伙分成 → **只写在线下合作协议里**，走公对公/对私转账 + 开票 | ❌ 小程序内实现"推荐得奖励"功能 |
| 线下谈成的 B2B 合作（介绍费属正常商业行为） | ❌ 小程序内展示分销层级、团队奖、管理津贴、见点奖、平级分红 |
| 如确需小程序内体现，层级严格 ≤2 | ❌ "变相无限代"的任何命名 |

## 2. 高风险问题（4 项）

### 🟠 P1-1 「微信支付分账」（原文 3.3 方案 A）个体户走不通

- 原文描述的是**服务商模式**（"服务商代替旗下特约商户发起支付交易后……分账"）→ 需**企业主体 + 微信支付服务商资质**。
- 原生分账还有约束：**单笔订单分账金额上限 30%**；分账接收方需具备相应主体资格。
- 分账必须由**收单商户**（或服务商代其）发起 → 让一家甜茶馆自己对接分账 API 不现实。

**结论**：**MVP 只用方案 B（月度对账）**，并按 §4 写实。方案 A 标注为「**升级企业主体 + 有交易量后**再评估」。

### 🟠 P1-2 LBS 定位推送很可能拿不到接口权限

- 自 **2022-04-18** 起，`wx.getLocation` 实行**准入开通**：**仅对部分类目开放**，需类目审核通过后在后台「开发与服务 → 开发管理 → 接口设置」自助开通。
- **工具类 / 内容类小程序通常无法开通**；申请理由需体现"到店核销 / 自提（门店列表 → 定位 → 最近门店）"这类强位置业务。
- 我们走教育 / 文化类目 + 去游戏化后，"按当前位置推送附近商家"的**用途与类目不符**，是高危驳回点。

**替代方案**：

- **主力改为用户手动选择目的地 / 城市**（我们本来就有"我想去林芝"这类设计的雏形）。
- `wx.chooseLocation`（用户主动在地图上选点）限制较少，可作退路。
- **13 个行业里所有"LBS 按当前位置推送"都要改写为"目的地选择 + 城市筛选"**（餐吧、咖啡、奶茶三处的"3 公里内"改为"所选城市内"）。

### 🟠 P1-3 「景点门票绑定用户实名信息」拿不到实名

- 小程序**没有公开的"获取用户实名信息"通用接口**；实名能力通常绑定支付 / 政务场景或需特定资质。
- 让用户手填身份证号属**敏感个人信息**，需单独同意 + 加密存储 + 最小必要，个体户教育类小程序成本与风险都过高。

**替代方案**：券绑 `openid` + **单用户限领 1 张** + 商家现场核对本人微信（提示语："请用您本人微信打开这张券"）。**不收集身份证。**

### 🟠 P1-4 「用户画像（年龄 / 性别）给商家」= 个人信息对外提供

- 《个人信息保护法》第 23 条：向第三方提供个人信息需**单独告知并取得同意**。
- 小程序也无法直接获取用户性别 / 年龄（需用户自填），数据质量本身就存疑。

**替代方案**：给商家的数据只出**聚合统计**——今日核销 / 待使用 / 累计、核销时段分布、复购率、与上月对比。原文"数据赋能"表的第 3 行「用户画像：年龄、性别、偏好」应**删除或降级为聚合口径**。

## 3. 修正后的核销技术方案（替代原文 3.2）

```
① 游戏内达标
   └ 云函数生成券（自研码，无金额）
      记录：code / openid / merchantId / status / expireAt

② 用户到店，点「立即使用」
   └ 前端向云函数换取一次性 token（TTL 5 分钟）
      二维码内容 = 短时 token（不是券码本身）

③ 商家端扫码
   └ 云函数校验：token 未过期 + 券 status = claimed + 该商家有权核销

④ 校验通过
   └ status: claimed → used，写入 usedAt / merchantId / 操作人 openid

⑤ 状态锁定，不可逆
   └ 如需撤销，走「限时撤销窗口」，云函数记操作日志
```

**与原方案的对应关系**：

| 原文设计 | 是否保留 |
|---|---|
| 券码唯一性、核销后锁定、禁止二次核销 | ✅ 保留 |
| 动态二维码 5 分钟过期、防截图转发 | ✅ 保留（二维码内容 = 一次性 token） |
| 核销率预警（20%-50% 正常，短时冲 80% 异常） | ✅ 保留 |
| 三状态 已领取 / 已使用 / 已过期 | ✅ 保留（`claimed` / `used` / `expired`） |
| 「核销事件回调通知」 | ⚠️ 那是**微信支付商品券**的能力，自研券用不上 → 改为云函数写核销日志 + 商家端 `onShow` 拉取 |
| 「商家助手」独立小程序 | ⚠️ 独立注册需**另付 300 元/年 + 独立审核**；建议 **同一个小程序内角色切换**，或二期再拆（见 §5） |

## 4. 月度对账（MVP 唯一结算方式）写实

| 项 | 做法 |
|---|---|
| 计费口径 | 按**核销记录**计费（未核销的领券不计）；核销金额由商家在核销时填写，或按双方约定的客单价固化 |
| 对账单 | 每月 1 日云函数生成上月对账单（按商家聚合：核销笔数 / 金额 / 费率 / 应付） |
| 商家确认 | 生成图片/PDF 发群，商家回复确认 |
| 收款 | 商家向个体户转账；**必须开服务费发票** |
| 退单 | 核销后 N 天内可撤销（撤销窗口内），撤销笔数不计费，超时锁死 |
| 争议 | 以云函数核销日志为准（含操作人 openid、时间戳、券码） |

## 5. 其余问题（非阻断，建议修正）

| 位置 | 问题 | 建议 |
|---|---|---|
| 四·二 **阶梯佣金** | **表格与说明自相矛盾**：表里 5%→8% 是"量越大费率越高"，但说明写"商家越积极，佣金越低" | 改为**递减**：0-50 次 **8%** / 51-100 次 **7%** / 101-200 次 **6%** / 200+ 次 **5%**。量越大费率越低才是超额激励 |

| 二·各行业「LV1-LV6 / 10-300 关」 | 与现有内容**严重脱节**：当前只有 **10 关 / 8 个字母 / 4 个图标**；成长阶梯规划也只有 12 阶段 = **120 关** | 门槛改为**按阶段**（第一阶段 1-10 关 = LV1），并把 LV5/LV6（200/300 关）标为"待内容扩充后开放" |
| 四·五 退出机制 | "平台连续 3 个月没带来核销，商家可无条件退出"隐含**效果承诺** | 改为"未达约定核销量可无责退出"，避免构成效果承诺 |
| 一·二 话术 | "我帮您带精准客户"若被理解为**保证效果**有风险 | 保持"带来曝光与到店机会"，不承诺到店人数 |
| 分享 / 祝福卡内的小程序码 | 平台规范 §5.8.1 不允许"生成二维码进行朋友圈传播" | 优先用官方 `onShareTimeline` / 分享卡片能力，不自绘二维码诱导朋友圈传播 |
| 二·景点「冬游西藏免门票」 | ✅ **信息正确**：第九轮「冬游西藏」**2026-10-15 至 2027-03-15**，除寺庙景区外全区 A 级景区免门票（西藏自治区文旅厅 2026-09-24 公告） | 原文"不要跟用户说赢价值 XX 元门票"判断**非常对**。建议补充：本轮**旅游客运价格不高于旺季 50%**（大车 ≤6 元/公里、中型 ≤4 元、小型 ≤3.5 元），可做成"冬游交通券"叙事；注意活动期与上线节奏对齐 |

## 6. 一处新增的平台红线（与商业化直接相关）

《微信小程序平台运营规范》§3.4：

> **一旦你选择了游戏类目，该类目将不可修改变更为其他小程序类目。**

含义：**类目选择是一次性、不可逆的**。加上 §5.7「类目不符」是高频驳回/下架项，结论是——

- 提审前必须把类目定死，**不能"先随便选一个上线，以后再改"**。
- 这进一步说明 [`business-model-v2.md`](business-model-v2.md) §3 的「去游戏化表述改造」是**阶段 0 的唯一任务**，且必须在首次提交审核之前完成。

另注：§3.9 规定未经允许**不得展示或推荐其他微信小程序**——所以"跳转微信小商店买手工艺品"必须走官方 `wx.navigateToMiniProgram`（并配好跳转白名单），不能自造跳转链路。
