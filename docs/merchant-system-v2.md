## 0. 结论先行

**v1 评审发现的问题分三类，替代思路也分三类：**

| 类型 | 问题 | 替代思路（一句话） |
|---|---|---|
| **技术选型错** | 核销组件调不起来、分账个体户走不通 | **自研券 + 月度对账**（系统全在我们手里） |
| **合规踩线** | 积分抵现金、裂变抽佣、LBS、实名、用户画像 | **砍掉资金流与计酬层，业务价值用别的方式补回来** |
| **商业模式弱** | CPS 按金额抽成 → 收入全押在日活上 | **升级为「定额服务费 + 文化联名 + 实物代销」三支柱** |

**一句话总纲**：**你在商户这件事上只做三件事 —— 发凭证、写记录、开发票。** 不碰钱（防二清）、不碰计酬（防分销）、不碰个人信息（防 PIPL）。

## 2. 六个核心替代设计

### 2.1 替代 P0-1：自研券 + 三层核销端

#### （1）先解决合规定性 —— 券**不承载金额**

这是最容易被忽略、但最关键的一步。

| 设计 | 定性风险 | 判断 |
|---|---|---|
| ❌ 平台发「满 100 减 20 券」 | 平台在**发行有价凭证**；若可变现/兑付 → 二清；若可充值 → 单用途预付卡口径 | **不要做** |
| ✅ 平台发「**到店体验凭证**」 | 平台只证明「该用户完成了学习任务」，**不承诺任何金额或折扣**。到店后给什么，由**商家自主决定**（那是商家自己的店内促销） | **推荐** |

一句话：**平台是"凭证发放方"，不是"优惠券发行方"。** 券面上不写金额、不写折扣，只写「恭喜完成第一阶段学习 · 凭此凭证到 XXX 店解锁专属体验」。折扣由商家在店内兑现。

#### （2）券状态机与数据模型（云开发）

```
coupons      { code, openid, merchantId, status, createdAt, expireAt,
               usedAt, redeemedByOpenid, note }
             status: claimed → used / expired   （状态锁定后不可逆）

merchants    { id, name, city, category, ownerOpenids[], 
               feeMode: 'flat', flatFee, contractNo, status }

redemptions  { id, codeHash, merchantId, operatorOpenid, at, 
               revokedAt, note }                 ← 核销日志，争议以它为准

statements   { month, merchantId, redeemCount, revokedCount, payable, status }
```

#### （3）三层核销端（关键升级：让**没有小程序能力的商家**也能合作）

原方案只有一个路径（商家扫码），实际推广时**大量小商家不会用**。改成三层，按商家能力递降：

| 层 | 形态 | 适用 | 实现 |
|---|---|---|---|
| **主** | 商家在我们小程序内**切换为商家角色**扫码核销 | 会用小程序扫码的商家 | 商家 `openid` 白名单鉴权 + `wx.scanCode` |
| **备** | **一次性核销链接**：用户点「立即使用」生成链接 → 转发/出示给商家 → 商家**点开即确认**（无需安装、无需登录） | 不愿装、不会扫码的商家（甜茶馆、老人店） | 链接带一次性 token（TTL 5 分钟、绑商家 ID、用后即焚） |
| **冷启动** | **人工核销**：我们运营代录 + 纸质签单对账 | 首 1-2 家验证期 | 后台录入 + 留纸质凭证 |

> 备选层的安全设计：token **一次性 + 5 分钟过期 + 绑定商家 ID**，且商家确认页展示券的持有人昵称供现场比对。防的是「链接被转发后他人冒领」。

#### （4）反作弊（沿用 v1 三道防线 + 补两条）

| 防线 | 机制 |
|---|---|
| 券唯一且不可转让 | 券码唯一；券绑 `openid`，他人打开提示「请用本人微信」 |
| 动态凭证 | 二维码/链接内容是一次性 token，**不是券码本身** → 截图转发无效 |
| 商家鉴权 | 商家 `openid` 白名单；非白名单无核销权 |
| 限领 | 单用户单商家限领 1 张；跨商家总量设上限 |
| **异常预警** | 核销率 20%-50% 正常，短时冲 80% 异常 → 自动告警 + 冻结该商家核销权 |
| **（新）撤销窗口** | 核销后 N 天内可撤销（撤销笔数不计费），超时锁死；撤销写操作日志 |

#### （5）不再需要的东西

| 原设计 | 处理 |
|---|---|
| 「核销事件回调通知」 | ❌ 那是微信支付商品券的能力 → 改为云函数写核销日志 + 商家端 `onShow` 拉取 |
| 「商家助手」独立小程序 | ❌ 另付 300 元/年 + 独立审核 → 同小程序内角色切换；二期再拆 |

### 2.2 替代 P0-2：异业互推 —— 用「护照联名印章」替代积分

原方案的「积分抵现金 + 平台兑付」必须删（与二清同源 + 预付卡/代币风险）。但**用户的收集动机是真的**，不能简单删掉就完事 —— 用项目已有的**护照体系**接管它。

| 原设计（删） | 替代设计（用） |
|---|---|
| 消费送积分 | **核销后盖一枚「商家联名印章」**（护照里已有印章位） |
| 积分抵现金 | 印章**不通兑任何现金**，只是收藏与纪念 |
| 平台兑付给商家 | **零资金流**：平台不兑付、不结算、不经手 |
| 「越多越赚」诱导 | 集齐 N 枚 → 得**电子纪念证书** + **由商家自己提供的**店内权益（券由商家创建、商家兑现，平台不经手） |

**为什么这样更安全**：
- 印章 = 收藏品，不是有价凭证 → 不触及预付卡/代币口径
- 权益由商家自主提供 → 平台不是发行方、不是兑付方
- 与「护照 = 总档案」的既有产品设计天然契合 → 不是新发明，是**已有功能的复用**

**异业互推本身保留**（纯内容引导，零资金流）：
```
✅ 用户在甜茶馆核销后 → 推送「附近合作唐卡体验馆，凭今日甜茶凭证享 9 折」（折扣由唐卡馆自己定）
✅ 唐卡馆核销后 → 推送「附近合作民宿」
❌ 不发积分、不抵扣现金、不兑付、不跨店通兑现金
```

### 2.3 替代 P0-3：商家激励 —— 线上零计酬，激励只在线下

**这条的原则是"物理隔离"**：小程序里**一行计酬代码都不写**。

| 保留（线下合同） | 禁止（小程序内） |
|---|---|
| 商家介绍费、区域合作分成 → 纸质合同 + 转账 + 开票，**层级 ≤ 1** | ❌ 「推荐得奖励」任何形式的线上功能 |
| 线下 B2B 合作（介绍费属正常商业行为） | ❌ 展示分销层级、团队奖、管理津贴、见点奖、平级分红 |
| 若必须线上体现 → **只做内容层署名**（"文化合作伙伴"） | ❌ 任何"变相无限代"的命名 |

**红线依据**：平台规范 §5.3（网赚）、§5.9（多级分销）；《禁止传销条例》口径下 **计酬层级 ≥3 层 + 人数 ≥30 可刑事立案**。
**安全表述替换**：把"推荐商家得 200 元"改为合同条款「**年度合作服务费 / 渠道开发费**」（B2B 正常支出，与"拉人头"无关）。

### 2.4 替代 P1-1：结算 —— 定额服务费的三条路线

分账走不通，但结算需求是真的。按投入递增给三条路：

| 路线 | 做法 | 门槛 | 何时用 |
|---|---|---|---|
| **路线 1 · 定额 + 月度对账**（MVP 推荐） | 对账单 = 核销笔数 × **固定单价**（或固定月费）；商家转账 + 我们开票 | 个体户即可 | **现在就做** |
| **路线 2 · 持牌第三方分账** | 对接持牌支付机构分账产品，资金进**持牌机构监管专户**，不经过我们账户；支持个体工商户作接收方、可突破 30% | 需商务对接 + 尽调 | 商家数 > 20 且需自动化时 |
| **路线 3 · 升级公司 + 服务商** | 注册有限公司 → 微信支付服务商 → 商家成为特约商户 → 原生分账 | 企业主体 + 对公账户 | 真做平台时 |

**⚠️ 路线 1 的一处关键改良：把计费口径从「核销金额 × 费率」改为「核销笔数 × 固定单价」。**
理由：按金额比例抽成，观感上仍是「按交易抽佣」，容易被往「变相支付结算」上靠；**定额**能显著降低这个风险，同时对账更简单、商家更容易接受。若商家坚持要挂钩金额，退一步用「按双方约定的固定客单价折算」，而非实时读取交易额。

**税务**：服务费必须开票。个体户小规模纳税人月销售额 10 万以下免征增值税（超出按 1%/3% 小规模征收率），经营所得个税另计。

**对账单要素**：核销笔数 / 撤销笔数 / 单价 / 应付 / 计费周期 / 双方主体与开票信息。

### 2.5 替代 P1-2：位置 —— 目的地选择，而不是定位

`wx.getLocation` 自 2022-04-18 起准入开通且**仅部分类目可申请**，教育/内容类拿不到；且"按当前位置推送商家"与类目不符，是高危驳回点。

**替代设计（而且体验更好）**：

| 原设计 | 替代 |
|---|---|
| 「你附近 3 公里内的甜茶馆」 | 「**你想去哪？** 拉萨 / 林芝 / 日喀则 / 山南 …」→ 按所选城市筛选 |
| `wx.getLocation` 自动定位 | 用户**主动选择**城市 / 商圈（无需任何位置权限） |
| — | 退路：`wx.chooseLocation`（用户主动在地图选点，限制较少） |
| — | **内容化增值**：与「冬游西藏」路线结合 → 「冬游路线站点」叙事 |

**13 个行业文案统一改写**：餐吧 / 咖啡 / 奶茶三处的「3 公里内」→「所选城市内」。

**顺带的战略收益**：用户主动表达目的地 = **真实的出行意向数据**，比被动定位更有商业价值，且不涉及位置隐私授权。

### 2.6 替代 P1-3 / P1-4：身份与数据 —— openid + 聚合统计

**身份（P1-3）**：不收集身份证。

| 需求 | 替代 |
|---|---|
| 门票 / 券要绑人 | 券绑 `openid` + 单用户限领 1 张 |
| 防止冒用 | 现场提示「请用**本人微信**打开此券」，商家核对微信昵称/头像 |
| 强核身诉求 | ❌ 不做。小程序无公开实名接口；手填身份证属敏感个人信息（需单独同意 + 加密 + 最小必要），个体户教育类小程序成本与风险都过高 |

**数据（P1-4）**：给商家的数据只出**聚合口径**。

| ❌ 原设计 | ✅ 替代 |
|---|---|
| 用户画像：年龄、性别、偏好 | **删除** |
| 明细级用户数据 | 今日核销 / 待使用 / 累计、核销时段分布、复购率、环比 |
| — | 全部**去标识化、聚合到商家维度**，不含任何可定位到个人的字段 |

依据：《个人信息保护法》第 23 条（向第三方提供个人信息需单独告知并取得同意）。**删掉这一行，风险归零，商家实际也用不到画像。**

| 位置 | 问题 | 修正后 |

## 4. 商业模式升级：从「纯 CPS」到「三支柱」

这是本文最重要的战略修正。v1 的收入模型是「核销次数 × 费率」，**收入 100% 押在日活上**（v2 测算：月核销 20 次 = 210 元，覆盖不了成本）。这不是合规问题，是**模型问题**。

| 支柱 | 收入来源 | 是否依赖日活 | 合规负担 | 定位 |
|---|---|---|---|---|
| **① 定额服务费** | 商家按月付固定服务费（或用系统年费） | **否**（签了就有） | 低 | **现金流底盘**，先签 3-5 家把成本覆盖住 |
| **② 文化联名合作** | 商家出资做「文化联名款」（联名文化卡 / 联名印章 / 联合署名） | 否 | 中（不得叫"广告位"） | **溢价来源**，客单价远高于服务费 |
| **③ 实物代销** | 代销商家文创 / 残疾人手工艺品，赚**差价** | 部分 | 低（走实物电商，见 monetization-v3 §4.2） | **上限来源**，且自带公益叙事 |
| ~~④ 按核销金额抽成~~ | ~~核销额 × 费率~~ | 是 | **高** | **降级为可选**，只在商家坚持时才用 |

**为什么这个组合更好**：
- ① 让收入**不再取决于用户来不来**，把「存量日活风险」换成「商家数量」这个你能主动推进的变量
- ② 把「广告位」这个需要资质的生意，换成**不需要广告资质的内容联名**，同时卖上价
- ③ 与 [`monetization-v3.md`](monetization-v3.md) 的引擎 B 打通，两份收入一次性变现
