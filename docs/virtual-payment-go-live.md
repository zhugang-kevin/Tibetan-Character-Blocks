# 虚拟支付上线清单（D113c · D136 补充操作单）

> 这份文档回答一个问题：**从「代码已就绪」到「真的能收到钱」，还差哪几步、谁来做。**
>
> 结论先说：代码侧**已全部就绪**（下单 / 签名 / 回调 / 查单 / 发货 / 限额 / 降级）。
> 剩下的两步是 **账号级操作**，只能由你本人登录微信后台完成 —— 任何 Agent 都代劳不了，
> 因为它需要法人身份证、对公银行卡、管理员扫码签约。
> 本文档把这两步做成**逐字可复制的表格**，照着填即可。

## 二、MP 后台开通流程

登录 <https://mp.weixin.qq.com> → 左侧栏【**支付与交易** → **虚拟支付**】→【**开通**】。

1. 阅读并勾选签署《虚拟支付服务协议》
2. 提交主体资料：营业执照 / 法人身份证 / 提现银行卡 / 支付管理员信息
3. **账户验证**：支付管理员**是法人** → 可跳过；**非法人** → 需账户打款验证
4. 管理员微信**扫码签约**
5. 等待平台审核：约 **1–7 个工作日**
6. 审核通过后自动生成**虚拟支付二级商户号**（独立于普通微信支付商户号，两者不可混用）
7. 再等约 1–2 个工作日进入商户管理模块

### 开通后要记下的 3 个参数

| 参数 | 是什么 | 在哪找 |
|---|---|---|
| **AppID** | 小程序的身份证号 | MP 后台 → 设置 |
| **OfferID** | 你的支付账号 | 虚拟支付 → 基本配置 |
| **现网 AppKey** | 支付密钥（另有**沙箱 AppKey** 一套） | 虚拟支付 → 基本配置 |

⚠️ `env` 决定用哪一套 AppKey：`env=0` 正式 → 现网 AppKey；`env=1` 沙箱 → 沙箱 AppKey。用混必失败。

### iOS 端额外前置条件

必须配置「**小程序简称**」（Apple 支付需展示 display name）。
入口：mp.weixin.qq.com → 虚拟支付 → 基础配置；配好后回到「基本配置」开通苹果 IAP 支付。
未配简称 → iOS 端开不了 Apple 支付。

## 二点五、三个参数怎么填进代码（D136 · 一条命令自检）

**开通后你只需要改一个文件：`config/pay.js`**（已在仓库里，里面没有任何密钥，所以可以提交）。

```js
// config/pay.js
module.exports = {
  offerId: '1450001234',                                   // ← 后台「虚拟支付 → 基本配置」的 OfferID
  env: 0,                                                   // ← 现网只能是 0
  orderApi: 'https://api.你的域名.com/pay/order',            // ← 你的服务端下单接口
  goodsPublished: true                                      // ← 4 个道具全部发布后才改 true
};
```

三点说明（都是为什么这么设计，不是废话）：

| 设计 | 原因 |
|---|---|
| **AppKey 不在这里** | 官方红线：签名只能在服务端算，AppKey/session_key 绝不能出现在前端。写进这里 = 泄密 + 用户可伪造支付 |
| **填一半会报错** | 全空 = 未开通（正常，入口隐藏）；**填一半 = 最危险**，自检直接判红 |
| **orderApi 有五条硬约束** | https / 非 IP / 非 localhost / 不要 `:443` / 不用 `api.weixin.qq.com` —— 全是官方《网络》文档原文 |

**改完立刻跑（不联网、不花钱）：**

```bash
node scripts/check-pay-config.js
```

它会查：有没有把密钥误写进前端 · 是否半配置 · offerId 是否为纯数字 ·
orderApi 是否踩了官方五条红线 · env 是否合法 · 道具价格是否以「分」为单位。

**7 个变异样本全部翻红、2 个合规样本不误判**（D136 已实测），所以它红就是真红。

脚本查不到、必须你人工确认的三条：
1. 域名**已完成 ICP 备案**
2. 域名已在小程序后台「开发 → 开发设置 → **服务器域名**」里配置（request 类型）
3. 证书非自签名 + **TLS ≥ 1.2**

> 代码侧读取顺序：`config/pay.js` → 若不存在则退回 `app.injectPaymentConfig(...)` → 都没有则 `isReady()===false`。
> 三种情况都不会崩、不会发请求、不会假装能付。

### 如果后台**看不到**「虚拟支付」菜单

不是 bug，是前置没满足。按官方条件逐条对：**已认证** + **主体为企业/事业单位/个体工商户** + **主体信息完备**。
（《虚拟支付：企业、个体户》开通条件只有这三条，原文没有提类目、版号、软著。）

## 三、道具申报表（4 个，逐字复制到后台「道具管理」）

**唯一事实源**：`data/goods.js`。前端 `utils/payment.js` 与服务端 `server/index.js` 都 require 它，
**两处都不再各写一份价格**（漂移即 -15013 / 显示价≠实付价）。validate §64.11 机械守卫这一点。

| # | 道具 ID（productId） | 价格（分） | 价格（元） | 道具名称 | 发货内容（give） |
|---|---|---|---|---|---|
| 1 | `tib_lamp_1` | `100` | ¥1 | 点一盏酥油灯 | `lamp` |
| 2 | `tib_blessing_3` | `200` | ¥2 | 送一句藏文祝福 | `blessing` |
| 3 | `tib_khata_6` | `300` | ¥3 | 献一条哈达 | `khata` |
| 4 | `tib_name_99` | `600` | ¥6 | 为 TA 取一个藏族名字 | `name` |

**注意**
- 道具 ID **区分大小写、逐字一致**；改一个字符就是另一个道具（未发布 → 报 `-15010`）。
- 价格单位是**分**，`600` 是 ¥6，不要写成 `6`。
- 后台发布后约 **10 分钟生效**；刚发布就下单会报 `-15014`。

### 道具图片（后台「添加道具」时上传）

图片在 `images/gift-icons/`，**文件名 = productId + `.png`**，逐字对应上表：

| 道具 ID | 图片文件 | 实际像素 | 体积 |
|---|---|---|---|
| `tib_lamp_1` | `images/gift-icons/tib_lamp_1.png` | 200×200 | 41.1KB |
| `tib_blessing_3` | `images/gift-icons/tib_blessing_3.png` | 200×200 | 78.4KB |
| `tib_khata_6` | `images/gift-icons/tib_khata_6.png` | 200×200 | 63.7KB |
| `tib_name_99` | `images/gift-icons/tib_name_99.png` | 200×200 | 88.5KB |

**平台硬要求**：PNG/JPG、**200×200**、**<200KB**（后台「批量添加道具」的图片链接还要带
`Access-Control-Allow-Origin: https://mp.weixin.qq.com/`）。上表四张已实测全部合规。

**设计口径（为什么是深底 + 金/彩主体，不是浅底）**：
微信付款弹窗是**白底**，浅底道具图会直接消失在白底里 —— 本项目曾用米白底画哈达、
纯白底画藏名卡，两张在真实尺寸下都「看不见」。
故统一为**深饱和漆地 + 高对比主体**（灯火=近黑褐、祝福卡=深绛、哈达=靛蓝、藏名卡=绛红织锦），
四张放在一格里也认得出是同一套。藏名卡中央是**真藏文**（Chrome + NotoSerifTibetan 渲染，
PIL 无 raqm 会排成断笔字，勿用 PIL 直接出图）。

> 这四张是**上传用**资产，**不进小程序包**（已在 `project.config.json` 的
> `packOptions.ignore` 里排除 `images/gift-icons`）。运行时礼物页用矢量/文字，不用位图。

## 四、服务端环境变量（部署时填）

服务端全部走环境变量，**不进代码库**（validate §64 会扫描禁止硬编码密钥）。

**模板已给：`server/.env.example`**（已提交，里面全是空值）。复制成 `server/.env`（已被 .gitignore 拦）再填：

```bash
cp server/.env.example server/.env
# 填完用 Node 自带的 --env-file 启动（本项目零依赖，没装 dotenv）
node --env-file=server/.env server/index.js
```

| 变量 | 含义 |
|---|---|
| `WX_APPID` | 小程序 AppID |
| `WX_APPSECRET` | 小程序 AppSecret（换 openid 用） |
| `WX_OFFER_ID` | 虚拟支付 OfferID |
| `WX_APPKEY_PROD` | 现网 AppKey（`env=0`） |
| `WX_APPKEY_SANDBOX` | 沙箱 AppKey（`env=1`） |
| `WX_ENV` | `0` 正式 / `1` 沙箱（**现网只能是 0**，否则 -15011） |
| `PORT` | 监听端口，默认 8787 |

**起完先自检（不花钱、不用真支付）**：

```bash
curl https://你的域名/health          # 期望 {"ok":true,"status":"up","configured":true}
```

`configured:false` = OfferID 或 AppKey 没读到，此时下单必失败（服务端启动日志也会打
「⚠️ 未配置 AppKey，下单会失败」）。**这一步过了再往下走**，能省掉一大半排查时间。

回调地址填在后台「消息推送回调地址」，**必须公网可访问的 HTTPS** —— 不可达则不会自动发货
（本项目有查单兜底：前端轮询 `queryOrder`，官方也建议服务端每 5 分钟主动查一次）。

> 运行时数据（`server/data/*.db`、`*.jsonl`、`server/.env`）**已在 .gitignore 里**：
> 订单表含 openid / 订单号，属于用户数据，不跟着代码走。

## 五、上线三步验收

1. **沙箱**：`WX_ENV=1` + 沙箱 AppKey，走完「下单 → 支付 → 回调 → 发货 → 查单」全流程；
   重点看发货**幂等**（同一单号重复回调不应重复入账）。
2. **现网小额**：`WX_ENV=0`，用 ¥1 的酥油灯真实付一次，确认收礼箱出现一条、灯火 +1。
3. **限额**：确认服务端三条限额生效（同一对好友 3 次/天、单人收 50 份/天、单账号 ¥50/天）。

## 六、错误码速查（来自 utils/payment.js#ERR，照官方文档抄）

| 码 | 含义 | 该怎么办 |
|---|---|---|
| `-15002` | 订单号重复 | 换新单号重试 |
| `-15005` | 用户态签名错误 | 服务端 `signature` 算错，查 session_key |
| `-15006` | 支付签名错误 | 服务端 `paySig` 算错，查 AppKey / env |
| `-15007` | session_key 过期 | 需重新 `wx.login`（本项目已带 code） |
| `-15010` | 道具 productId 未发布 | 去后台「道具管理」发布 |
| `-15011` | 现网版本 env 只能是 0 | 改 `WX_ENV=0` |
| `-15012` | 米大师失败导致关单 | 换新单号重试 |
| `-15013` | 道具价格与后台不一致 | 以 `data/goods.js` 为准核对后台 |
| `-15014` | 道具发布未生效 | 等约 10 分钟 |

## 七、边界（如实说明）

- **代码能做的都做完了**：下单前限额、DB 主键幂等、弱确认→查单、未配置优雅降级、三条红线机检。
- **代码做不到**：微信认证、备案、虚拟支付开通与签约、后台道具发布 —— 都需要你的主体身份与扫码。
- **未配置时不会假装有支付**：`payment.isReady()` 为 false，礼物页显示「祝福通道还没开通」且按钮禁用。
