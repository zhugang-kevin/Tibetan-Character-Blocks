# 藏字方块 · 商业化方案 v2

> 更新：2026-10-04 · 校准设定：**微信小程序（非小游戏）+ 个体工商户 + 无广告**
> 变现路径：商家核销 CPS / CPA + 残疾人公益导流 + 线下服务费
> 前置阅读：[`docs/release-and-monetization.md`](release-and-monetization.md)（开通流程与材料）

---

## 0. 结论先行（三句话）

1. **能做的**：个体户可开通微信支付商户号（费率 0.6%~1%，享小微 9 折，**该优惠已续期至 2027-09-30**）；可用经营者个人卡结算；可自研「核销码」做商家核销闭环（**不碰资金**）；可与商家签服务合同收导流服务费。

2. **不能做的**：
   - ❌ 小程序内**虚拟内购**——虚拟支付开通条件是「个体工商户或企业 + **已认证小游戏** + **版号** + 软著自审报告」，而**个体户无法自行申请版号**（资质不符），只能授权使用他人已获批版号。结论：内购线关闭。
   - ❌ 用**微信原生分账自动抽佣**——原生分账门槛为**企业主体 / 微信支付服务商资质**，分账接收方须为**企业主体且拥有独立商户号**，且**单笔订单分账上限 30%**。个体户走不通。
   - ❌ **代收交易款再转给商家**（「资金先归集到你的商户号，再拆分给商家」）——这是**无证二次清算（二清）**，央行银发〔2016〕217 号文红线，会触发通道关停、资金冻结、行政处罚。**这条是绝对禁区，不是「尽量别做」。**

3. **必须先解决的闸门**：**服务类目判定**。我们的产品有「10 个关卡 + 积分 + 连击 + 金色方块 + 印章收集」，属于典型**游戏元素**；以「教育 / 工具」类目申报极易被判定「类目与内容不符」直接驳回——这是 2026 年最高频的驳回理由。**这一关不过，后面所有商业化设计都没有落地面。**

## 2. 三条收入线的合规资金流

### 2.1 商家核销（CPS / CPA）—— 只收服务费，不碰交易资金

**❌ 违规架构（二清）**

```
用户在小程序内付款 → 资金进「你的」商户号 → 你按比例转给商家
        ↑ 资金归集 + 二次清算 = 无证支付业务，红线
```

**✅ 合规架构（推荐）**

```
① 用户在小程序里领一张「核销券」（券 = 一串自研码，无金额、无支付）
② 用户到店消费，用商家自己的收款码全额付款 → 钱直接进商家账户
③ 商家在「商家端」扫码核销该券 → 系统写一条核销记录（时间/商家/券号）
④ 月度对账：核销金额 × 约定费率 = 导流服务费
   商家向你的个体户付款（对公转账或对私转账均可），你开服务费发票
```

**技术含义**：小程序里**没有任何支付代码**，只有「券的状态机」。资金全程绕开你。

**合同必备条款**：费率与计费口径（按核销金额 / 按到店人数）、结算周期、**退单与撤销核销规则**、核销凭据留存、双方主体与开票信息、数据归属（核销数据你可否用于对外披露）。

### 2.2 残联手工艺品导流 —— 平台外成交，收运营服务费

```
小程序内展示匠人手工艺品 + 匠人故事 → 用户点「去购买」
→ wx.navigateToMiniProgram 跳转对方「微信小商店」→ 在对方店铺成交与履约
→ 你按成交额收 5%~10% 运营服务费
```

- **技术前置**：需在微信公众平台后台配置「可跳转的小程序」白名单（关联对方 AppID，需双方授权），一般可关联 10 个。
- **你不碰货、不碰钱、不碰售后**，只做展示与导流——这是最轻的合规负担。
- **合规红线**：
  - 不得出现「**募捐 / 捐款 / 慈善募捐 / 献爱心**」等表述——那属于《慈善法》下的公开募捐，需要资质。你用「公益合作」「助残导流」等商业表述。
  - 「公益贡献值」按**营销积分**设计（可兑换的是**优惠券**，不是现金、不是实物兑换资金），避免被认定为变相资金募集。
  - **匠人故事必须真实可核**，不得虚构；残疾人创作者身份不得用于道德绑架式营销（会被判定为不良营销）。
  - 分成参考：售价 100 元 → 创作者 70-80 元、你 10-15 元、其余覆盖平台成本。**注意**：5%-10% 的服务费在扣除自己的开票与运营成本后实际净得可能只有 5-8 元/单，收入贡献有限，定位应是**品牌差异化而非主要收入**。

### 2.3 本轮明确排除

| 排除项 | 原因 |
|---|---|
| 小程序内虚拟内购 | 版号不可得（§0.2） |
| 广告 / 流量主 | 你的设定（无广告） |
| 会员 / 储值 / 预付费 | 「预付费自主清算」是监管重点整治场景，风险极高 |
| 微信原生分账自动抽佣 | 资质门槛不适配（§0.2） |
| 代收代付 | 二清，绝对禁区 |

## 3. 最大的技术风险：类目判定（第一优先级）

### 3.1 问题

微信审核把「类目与内容不符」列为**最高频驳回原因**。我们的文案与功能里游戏特征非常明显：

| 现在 | 特征性质 | 建议改法 |
|---|---|---|
| 「第 N **关**」、10 个关卡 | 关卡 = 游戏标志 | 「学习单元 1-10」/「第 N 课」 |
| 积分 / score | 计分 = 游戏标志 | 「学习得分」/「识记掌握度」 |
| 连击 ×N / combo | 连击 = 游戏标志 | 「连续正确 ×N」/「无错连读」 |
| 金色方块 ✦（双倍积分） | 道具加成 = 游戏标志 | 「重点字（双倍练习）」 |
| 印章「拉萨」收集 | 成就系统 | 「文化收藏印章」 |
| 引导页「如何消除」 | 玩法教学 | 「如何使用」/「学习方式」 |
| Slogan「玩方块，认藏文」 | 含「玩」 | 备选：「认藏文，从方块开始」／「藏文启蒙，从字块起步」 |
| 标题「藏字方块」 | 中性 ✅ | 可保留 |

### 3.2 两条路，只有一条能走

| 路线 | 可行性 | 说明 |
|---|---|---|
| **A. 教育 / 文化类目**（推荐，唯一可行） | ✅ | 优势是**教育属性真实**：每个元素都有文化知识卡 + 发音 + 成长阶梯 + 证书体系，不是包装。必须配合上述「去游戏化」文案改造 |
| B. 小游戏类目 | ❌ **当前设定下不可选** | 个体户做轻休闲小游戏**必须走广告变现**才免版号；你已定「无广告」→ 无变现通路；且企业主体做小游戏无论是否内购都需版号 |

**结论**：**必须走 A，并把「去游戏化」表述改造列为阶段 0 的第一件事。** 这不是文案洁癖——它决定能不能上线。

### 3.3 证据链（审核时可提交的材料）

- 软件著作权（必须，个体户可作申请主体，1-2 个月，代办约 800-1500 元）
- 游戏自审自查报告（若不判为游戏可免；判为游戏则必交，模板在微信开放平台下载）
- 每个元素的文化知识卡 + 藏语发音（教学属性的直接证据）
- 藏文排版规范文档 [`docs/tibetan-typography.md`](tibetan-typography.md)（专业性佐证）
- 成长阶梯与证书体系 [`docs/certificate-system.md`](certificate-system.md)（学习路径佐证）
- **不要**在提审版本里预埋任何支付代码（无商户号时提交会直接驳回）

## 4. 成本与收入（修正版）

### 4.1 成本

| 项目 | 性质 | 金额 |
|---|---|---|
| 个体工商户执照 | 一次性 | 0（自办）~ 500（代办） |
| 微信认证 | **年** | 300 元/年 → 25 元/月 |
| ICP 备案 | 一次性 | 0（必办，1-20 工作日） |
| 软件著作权 | 一次性 | 800 ~ 1500（代办，1-2 个月） |
| 云开发 | 月 | 0 ~ 200（免费额度内可 0） |
| 域名 + HTTPS | 月 | 0（用云开发可省）~ 4 |
| 代理记账（建议） | 月 | 200 ~ 300 |
| **经常性合计** | 月 | **约 30 ~ 230 元**（不含记账）/ 含记账 230 ~ 530 元 |

**税费**：个体户小规模纳税人月销售额 10 万元以下免征增值税；经营所得个税按 5%~35% 或核定征收。MVP 阶段基本可忽略，但**开票与报税义务从第一笔服务费收入就存在**，这是真实成本。

### 4.2 收入敏感性（关键）

假设：商家核销服务费率 10%、客单价 80 元；公益导流 20 单 × 100 元 × 10% = 200 元。

| 月核销次数 | 商家服务费 | 公益导流 | 合计 | 能否覆盖成本 |
|---|---|---|---|---|
| 20 | 160 | 50 | **210** | ❌ 覆盖不了（含记账则明显亏损） |
| 100 | 800 | 200 | **1000** | ✅ 可以 |
| 300 | 2400 | 400 | **2800** | ✅ 健康 |

**结论**：收入的唯一杠杆是**核销次数**，而核销次数 = 日活 × 到店转化率。**留存是商业化的前置条件，不是并行项。** 这也正是成长阶梯 + 证书体系（30 天留存模型）必须继续做厚的原因。

## 6. 修正版行动路线图

```
阶段 0（现在，最高优先级）── 去游戏化表述改造 + 软著准备
   └ 所有商业化的前提。不过审核，后面全是空谈。
             │
阶段 1 ── 执照 → 微信小程序注册（个体户主体）→ 微信认证 300/年 → ICP 备案
             │
阶段 2 ── 开通微信支付商户号（仅用于收服务费 + 开票，不接小程序内支付）
             │        ▲ 可与阶段 3 并行
阶段 3 ── 核销闭环 MVP（云开发 + 券状态机 + 商家端扫码）
             │
阶段 4 ── 签约 1-2 家甜茶馆 / 咖啡馆，跑通「第一笔真实核销」
             │
阶段 5 ── 残联对接（不可控，尽早启动）+ 公益模块
             │
阶段 6 ── 种子内测 → 看 7 日留存是否 > 25% → 决定是否扩商家
```

**顺序上的一处修正**：你的路线图把「签约商家」放在「开发 MVP」之后——方向对，但**类目改造必须先于一切**，否则签了商家也上不了线。另外**残联对接周期不可控**，建议与商家签约并行启动，不要排成串行。

## 7. 需要你拍板的 3 件事

1. **类目路线**：确认走 A（教育 / 文化类目）并接受「去游戏化」表述改造？（这是唯一可行路线，但会改动不少现有文案与 Slogan）
2. **用户身份边界**：是否允许引入静默 openid？券/核销必须绑定用户，而原始红线是「不做登录」。我的建议是允许，但严格限定用途（仅券绑定与防刷，不做账号、不收手机号、不索取头像昵称）。
3. **第一条收入线**：先做商家核销闭环，还是先做公益模块？我建议**先核销闭环**——公益导流依赖残联对接进度，不可控，不适合做第一条验证线。
