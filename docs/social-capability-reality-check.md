## 一、决定性事实：我们是「小程序」，而这些能力是「小游戏」独有的

### 当前项目形态（已核实）

```
project.config.json → compileType: "miniprogram"
app.json → pages 数组（6 个页面）
game.json → 不存在
```

**这是一个标准的微信小程序（mini-program），不是小游戏（mini-game）。**

### 平台能力的硬边界（有出处）

| 出处 | 原话 |
|---|---|
| 腾讯云开发者社区 | 「关系链数据使用这个功能，**从 H5 到普通小程序**，除了一些腾讯内部自己做的一些应用里实现过外，**外界是从来没有办法去实现的**。而现在，**小游戏具备了这个能力，它是唯一一个能呈现关系链数据的应用形态**。」 |
| InfoQ（微信团队技术分享） | 「在 H5、**普通小程序**与小游戏之间的区别中，目前**小游戏是唯一一个真正支持关系链数据使用方案的**。」 |
| 官方文档路径本身 | 关系链互动提醒／擂台赛／开放数据域 全部挂在 **`developers.weixin.qq.com/minigame/...`**（minigame = 小游戏）路径下，**小程序文档里没有** |

### 因此，我上一轮给你的方案里，以下四项**在当前形态下全部不可用**

| 能力 | 小程序能否用 |
|---|---|
| 好友排行榜（`wx.getFriendCloudStorage`） | ❌ **不能**（需开放数据域，小游戏独有） |
| 关系链互动提醒 | ❌ **不能**（小游戏独有） |
| 在玩朋友 / 排行榜超越提醒 | ❌ **不能**（依赖关系链） |
| 擂台赛组件 | ❌ **不能**（小游戏独有） |

**⚠️ 我上一轮把「关系链互动提醒」「擂台赛」写成可行方案，是没有先核实产品形态就下的结论。这是我的错。**
**是这次动手前的核实把问题挡住了 —— 如果直接开工，会白做几个星期的活。**

## 二、那「A 不分享 B 怎么知道」这个问题，在小程序上还有解吗？

**有，但完全是另一条路。** 小程序能用的社交能力只有这些（其余都得靠后端）：

| 能力 | 小程序可用 | 能实现什么 |
|---|---|---|
| **分享卡片（带参数）** | ✅ | A 分享 → B 点开 → B 进入**同一关**挑战（A 的分数写在卡片参数里） |
| **分享到群** | ✅ | 群里所有人都能参与同一个挑战 |
| **订阅消息（服务通知）** | ✅ | 可主动通知用户（**但每次需用户授权订阅**，不像小游戏的「订阅一次永久有效」） |
| **群 ID（`wx.getGroupEnterInfo`）** | ✅ | 从群卡片进入时能拿到群标识 → 可做「同一个群的战绩榜」 |
| 好友列表 / 关系链 | ❌ | **拿不到** |

### 关键约束：跨用户数据需要后端

- **无后端**：B 的成绩传不回 A（纯本地，D3 规定无云函数）→ 只能做「A 立靶子，B 本地对比」，**A 永远不知道 B 来了**
- **有后端**：才能实现真正的「挑战链」（A→B→A 闭环）

**所以要在这条路上走通，必须先回答一个问题：是否引入后端/云开发？**
这与现行约定（D3：纯本地、无云函数）**直接冲突**，是一个必须由你拍板的架构决策。

## 三、三条可选路径（请选一条）

### 路径 A：迁移为「小游戏」（能力最全，但工作量大）

**得到**：好友排行榜、关系链互动提醒、在玩朋友、擂台赛、微信礼物 —— **我这轮给你的全部方案都能用**。

**代价**：
- 小游戏**没有 WXML/WXSS**，UI 必须用 Canvas 重画 → 现有 6 个页面（首页/游戏/结算/证书/护照/…）都要重写
- 游戏逻辑（`utils/grid.js` 排版、`data/learning.js` 关卡、`data/elements.js`、音频、字体）**可以复用** —— 这部分是我们最重的资产，已实测且成熟
- 估算：**UI 层重写 + 排行榜/提醒接入**，是本项目开工以来最大的一次改造

**适合**：如果社交裂变是核心增长策略（官方数据：社交注册占 30-50%、部分 IAA 80% 收入来自社交场景），这个投入是值得的。

### 路径 B：保持小程序，做「轻量分享挑战」（改动小，但 A 不知道 B 来了）

**做法**：A 通关 → 生成带分数的挑战卡 → 分享到群/好友 → B 点开进入同一关 → B 看到「A 的成绩 X，你能超过吗」→ B 玩完看到自己的对比。
**通知 B**：靠**群里的卡片**（天然可见），不靠关系链。

**改动**：只需在分享卡片里带参数 + 一个「挑战进关」入口。**无需后端、无需迁移、不违反 D3。**

**代价**：A **收不到** B 挑战的结果（无后端）；没有好友榜；没有超越提醒。

### 路径 C：A + B 都做（先 B 顶着，再评估是否迁 A）

**做法**：先用路径 B 把「分享挑战」做出来（成本低、可上线验证）；同时把「是否迁移小游戏」作为**独立决策**单独立项评估。

**我推荐 C**，理由：
1. 路径 B 能**立刻**解决一部分「A 不分享没人知道」的问题（分享到群 = 群里可见）
2. 迁移小游戏是**重决策**，应该基于「社交是否是我们的增长主线」来判断，而不是顺手做
3. 先把轻量版跑起来，能拿到真实数据再决定要不要重投

## 四、我需要你拍板的一件事

> **我们的增长主线，是「社交裂变」吗？**

- **是** → 走路径 A（迁移小游戏）。因为只有小游戏才有关系链能力，而社交裂变的全部官方工具都建立在关系链上。
- **否 / 还没想好** → 走路径 C：先做轻量分享挑战，**不迁移**。

**在得到这个答案之前，我不动手写社交功能** —— 因为两个方向的代码结构完全不同，写错方向等于白写。
