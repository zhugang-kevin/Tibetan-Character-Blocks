## 为什么是这 9 条

对这 9 条，厂商侧的表现是稳定的空产物，不是偶发、也不是限流：

| 写法 | 服务返回 |
| --- | --- |
| 裸字形 `ག` | **一个音频字节都不返回** |
| 加任何元音符号（`ཱིེོུ`） | 固定 **30ms、峰值 10~34** 的静音桩 |
| 其余 14 种写法变体 | 同上，全失败 |

对照：**同一分钟**里发出的 `གལ` / `གས` / `གངས་རི་` 全部正常出声。
40+ 次请求（间隔 6~10 秒）全失败 → 已排除限流 / 网络 / 鉴权，确属模型发不出这几个独立音节。

## 收到录音后的三步（开发者）

```bash
# 1. 先把文件放进 audio/voice/，然后体检——确认真的有声
python scripts/check_voice.py letter_03

# 2. 统一压缩（MP3 / 16k / 单声道），并清掉源 WAV
python scripts/compress_voice.py

# 3. 把 KNOWN_BLOCKED 里已经录好的条目删掉（scripts/gen_voice.py），
#    否则 §47 的「缺口只允许是台账已登记项」会继续放行、包体却多了文件
node scripts/validate.js

# 4. 重建浏览器体验版，新录音才会被内联进去
node scripts/build-h5.js
```

## 体检判据（为什么要体检）

D56 的核心教训：**文件存在 ≠ 文件有声**。近静音的音频文件同样是正常大小、
播放器也不报错，表现就是「点了没声音」，而且从代码里查不出来。所以录音也要过同一道闸：

- 时长 ≥ 0.25s
- 峰值 > −32 dBFS（低于此基本是底噪）
- 单声道 / 16000Hz
- 单条 ≤ 40KB

判据在 `scripts/check_voice.py` 顶部，与 `scripts/gen_voice.py` 的 `MIN_DUR` / `MIN_PEAK` 同源，改一处记得同步另一处。
