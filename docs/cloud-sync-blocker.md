# 🔴 云同步接线的硬阻断：SDK 507KB 装不进主包（D93）

> 本轮尝试把云服务接到小程序上，**卡在一个硬数字上，如实记录。**
> 云服务本身已开通可用；卡的是**打包体积**。

---

## 一、事实（都是实测数字）

| 项 | 数值 |
|---|---|
| 微信**主包硬上限** | **2048 KB**（2MB） |
| 我们自留的预算 | 1843 KB（= 硬上限留 10% 给编译产物） |
| 接入前的包体 | **1837 KB** |
| 云同步代码（4 个文件） | +15 KB |
| **云服务 SDK 的小程序构建产物** | **+507 KB**（`miniprogram_dist/miniprogram.js` = 519,582 字节，单文件） |
| **接入后合计** | **约 2359 KB** |
| **超出硬上限** | **约 311 KB** |

**结论：不是「紧一点」，是根本装不下。** 就算把自留预算全部用掉（顶到 2048KB 硬上限），
仍超 311KB —— 需要从别处腾出 **311KB**。

**为什么 SDK 这么大**：它是一份**预构建的单文件 bundle**（database + auth + storage + llm 四个模块
全在里面），小程序构建不做 tree-shaking —— 我们只用 auth + database，但四个模块的体积都得背。

---

## 二、三条可选路径

### 路径 A：做成**分包**（微信的标准解法，我推荐）

微信的规则：**主包 ≤ 2MB，分包各自 ≤ 2MB、总包 ≤ 20MB**。
把云同步（SDK + 调用代码 + 一个页面）整体放进分包，主包**不受影响**。

- **得到**：云同步可用；主包体积不变（仍 1837KB）
- **代价**：用户点「云同步」时才下载那 507KB 的子包（**按需加载，不拖慢启动**）
- **注意**：分包产物要放在子包目录内（`构建 npm` 默认产出在根目录，需确认放法），
  这一条**需要真机/开发者工具验证**，我没法在这个环境里验证构建结果

### 路径 B：从主包腾出 311KB

- 图片 801KB + 音频 583KB = 1384KB，砍 311KB ≈ 砍掉 **22% 的资产**
- **代价明确**：观感/音质下降。**我不推荐** —— 为了一个可选的同步功能牺牲全站观感，不划算

### 路径 C：不走云 SDK，改用**我们自己的服务端**

- 我们**已经有服务端**（`server/`，为虚拟支付而建），它同样能存进度
- **得到**：**零额外包体**；不新增依赖
- **代价**：没有 RLS —— 用户隔离要**自己在服务端实现**（按 openid 隔离），
  少了一层「数据库层强制」的保障；且服务端多一份要维护的逻辑
