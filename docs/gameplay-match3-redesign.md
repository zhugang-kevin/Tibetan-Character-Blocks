# 玩法改造：从「对对碰」到真正的三消（2026-10-20）

> **阅读顺序更新（2026-10-22）：先读第十三节「项目边界、十分钟续跑与19问校正」。** 第十三节的操作边界和调度要求优先于第十二节；第十二节检测结果是当时快照，实施前须复核。第十一节11.8—11.9记录此前用户确认；新补充的唐卡方向见第十三节。前文保留历史记录，不是全部有效决策。审查建议不是已实施功能，也不代表已验证留存与盈利。

> 起因：用户指出「这个游戏看起来像麻将（对对胡），我们做的是消消乐；
> 现在一对一对地消，没有挑战、没有娱乐、没有刺激，缺乏游戏的本质；
> 参考全网消消乐是怎么做的 —— 一对有效果、三个不同、四个又不一样，会不会更好」。

**结论先说：用户判断是对的，现状确实不是三消。** 下面是查证与改造方案。

---

## 一、诊断：我们现在到底是什么

### 现状机制
- 点选**任意两个相同的牌**（不要求相邻）→ 消除 → 下落 → 补池。
- 每张牌有唯一 `uid`，配对按 `id` 相同判定；盘面维持「池 / 在场 / 已消」三条守恒。

### 它对应的是哪一类
这是 **对对碰 / 连连看** 一类的「配对消」，
**不是三消**（Match-3）。差别不是措辞，是结构性的：

| 维度 | 三消（消消乐） | 我们现状 |
|---|---|---|
| 操作 | **交换相邻**两个元素 | 点选任意两个相同 |
| 消除条件 | 交换后形成 **3 个以上成线** | 两个 `id` 相同即可 |
| 下落与连锁 | 下落→**自动触发新的三消→连锁** | 有下落，但**不会自动连锁**（因为不要求相邻成线） |
| 特殊道具 | 4 消 / L·T 消 / 5 消 → 三种特效 | **无** |
| 关卡目标 | 限步数内完成分数/收集/清障等目标 | **无目标**，清空即结束 |
| 策略深度 | 每一步都在算「换哪里能出连锁/出特效」 | 找两个相同的就行 → **无决策** |

→ **用户的三个判断（没挑战、没娱乐、没刺激）在结构上成立**，
根因是：**缺少「连锁」和「特效」这两台引擎**，而不是难度没调好。

## 二、消消乐的标准机制（全网通行范式，非某一家独有）

### 2.1 五步核心循环
```
交换 → 匹配检测 → 消除 → 下落 → 连锁（回到匹配检测）
```
关键在**最后一步**：下落之后如果又凑成新的三消，就自动再消一次 ——
**玩家一次操作可能引发一大片爆炸**，这就是「爽感」的来源。
**没有连锁，就没有爽感**；我们再怎么调分都补不回来。

### 2.2 特效阶梯（这正是用户问的「一对/三个/四个不一样」）
| 消除形态 | 生成物 | 效果 |
|---|---|---|
| **3 个成线** | — | 普通消除 |
| **4 个成线** | 条纹 | **消除整行或整列** |
| **5 个成 L 形 / T 形** | 爆炸 | **清除周围 3×3** |
| **5 个成一线** | 彩虹/魔力鸟 | **清除全场同色** |
| 两个特效交换 | 组合 | 十字范围 / 全同色引爆（高阶） |

### 2.3 挑战从哪来
- **限步数**：每关固定可用步数，用不完的转化为奖励 → 逼玩家算「一步多用」。
- **关卡目标**：分数 / 收集指定数量 / 清除障碍 / 把物品运到底部 —— 目标不同，打法就不同。
- **障碍物**：冰块（多层，逐层破）/ 藤蔓（锁死不能动）/ 毛球（普通消除打不掉，只能特效炸）/
  毒液（每回合蔓延）/ 传送门。
- **难度曲线**：元素种类 5 种为宜（太多难匹配、太少没挑战）；棋盘 8×8 是验证过的黄金尺寸。

> 出处：多份三消玩法解析与开发文档（2026-10 检索）。以上是**行业通行设计**，不是某款游戏的私货。

## 三、改造方案（贴合「藏文学习」，不做通用山寨）

### 3.1 核心改动：配对 → 成线三消
| 项 | 现状 | 改为 |
|---|---|---|
| 操作 | 点两个相同 | **交换相邻两牌**（不成立则弹回） |
| 消除条件 | 两个 `id` 相同 | **横向/纵向 3 个以上同 `id` 成线** |
| 连锁 | 无 | **下落补齐后自动再检测**，连锁累加 |
| 盘面生成 | 每种元素**偶数**（保证配对消） | 每种元素**3 的倍数**，且**开局无现成三连**（否则白送） |
| 关卡校验 | 「逐关打到清空」 | 「逐关在**目标 + 步数**下可完成」，且**存在解** |

### 3.2 特效阶梯（用户要的「三个/四个不一样」，落到藏文）
| 消除 | 特效 | 藏文化命名 | 效果 |
|---|---|---|---|
| 3 连 | 普通 | — | 消除 |
| 4 连一线 | 条纹 | **笔锋** | 清整行 / 整列 |
| 5 个 L/T | 爆炸 | **字块碎裂** | 清周围 3×3 |
| 5 连一线 | 彩虹 | **同字归一** | 清全场同色 |
| 连锁 ≥3 | 倍率 | **连续正确** | 得分倍率递增（沿用现有连击模型） |

> 命名沿用项目已有的「去游戏化」口径（不用「关卡/积分/连击」这类词），
> 特效名取藏文字形语义，不是硬套。

### 3.3 关卡目标（解决「没挑战」）
每课一个目标，**与教学内容绑定**（这是我们的差异化，通用三消没有）：

| 目标类型 | 例子 | 教学结合 |
|---|---|---|
| 收集 | 本课 3 个新字母各收集 5 个 | 反复识别本课字母 |
| 清障 | 破掉 N 层冰霜 | 障碍下的牌是本课易混字母 |
| 限步 | 12 步内完成上述目标 | 逼玩家算连锁 |

### 3.4 棋盘尺寸与元素种类
- **元素种类**：每关 **5 种**（含本课新字母 + 已学字母复习）。
- **棋盘**：保持现有尺寸档位，但**最小不小于 6×6**（5×5 做三消过紧，很难出 4 连）。

### 过程中抓到的真 bug（不是用例问题）
`resolve` 里曾写「池一空就 break」，导致**最后一轮连锁被吞掉**（cascades 恒为 1）。
池空只影响「下一轮补不补」，不影响「这一轮消完后盘面上已经形成的线」。
→ 修正后 cascades 才能 ≥ 2。**如果没写这条测试，这个 bug 会一路带到线上，连锁等于没做。**

引擎目前**独立存在**，页面仍走老的配对消。原因：接入是一次**原子变更**，必须同时动
`pages/game/game.js`（交换操作）、`preview/template.html`（体验版镜像）、
`scripts/test-all-150.js`（校验口径）、`data/level-fingerprint.json`（关卡指纹）。

## 八、⚠️ 切换到三消时实测出的**硬约束**（2026-10-20，150 关全量跑出来）

**结论：我原先的"P1 先做引擎、P2 再做目标"的分期是错的。**
三消的「清空盘面即通关」在数学上**对 80/150 关不成立** —— 必须把**目标化**和机制切换**一起做**。

### 实测数据（scripts 一次跑完 150 关）

| 指标 | 结果 |
|---|---|
| 总关卡 | 150 |
| 格数**能被 3 整除**（有可能铺成纯 3 倍数） | **70 / 150** |
| 格数**不能被 3 整除**（必然留 1~2 张永远凑不成三连） | **80 / 150** |
| 实际生成后「每种元素在盘面上都是 3 的倍数」 | **14 / 150** |
| 开局就**没有任何合法交换** | **41 / 150** |

### 为什么会这样（不是实现疏忽，是数学）
1. **配比是 3 的倍数，但格数不是** —— 例如 5×5 = **25 格**，
   `25 % 3 = 1` → 无论怎么铺，盘面上必然有元素的张数不是 3 的倍数 → **那 1~2 张永远消不掉** → 盘面清不干净。
2. **一次消除拿掉的是"整条线"**（长度 ≥3，任意长），不是固定 3 张 →
   某元素的剩余量会停在 1 或 2 → 同样消不掉。
3. 所以三消类游戏**从不以"清空盘面"为通关条件**，行业标准是
   **限步数 + 关卡目标**（打消 N 个 / 收集 X / 清障碍）。这不是风格选择，是**机制自洽的必要条件**。

### 因此正确的切换方式（修正后的计划）
**三消机制 + 目标化，必须作为一个整体上线**：

| # | 必须一起做的 | 为什么不能分开 |
|---|---|---|
| 1 | 通关条件：清空盘面 → **限步数 + 目标达成** | 清空在 80 关数学上不可能 |
| 2 | 盘面生成：保证**开局有合法交换** | 实测 41/150 开局就动不了 |
| 3 | 元素余量不再要求"3 的倍数" | 目标模式下允许有剩余，余量约束可以彻底去掉 |
| 4 | 死局检测 + 洗牌 | 目标模式下仍可能出现无步可走 |

> 已完成的（可保留）：`utils/match3.js` 引擎（22/22 验证）+ `distribute3` +
> `createLevelMatch3`（开局无三连）。这些是地基，不会白做。
> **但页面绝不能现在切** —— 切了就是 80 关直接不可通关。

### 9.2 必须先纠正的历史判断

1. 「没有连锁就没有爽感」「配对无决策」「8×8 黄金尺寸」都不是普适定律。配对可由空间、资源和目标产生策略；三消也可能无聊。本项目必须用实际选择分歧和试玩验证。
2. 格数不能被 3 整除，**不能证明三消无法清空**：允许 4、5 连时每次消除量不固定为 3，特效还能清除额外格子。有限池确有卡死风险，但必须以完整规则和具体反例论证，不能用整除关系替代证明。
3. 「三消从不以清空为目标」过度绝对。此处建议目标制，是因为适合当前有限池与玩法诉求，不是所有游戏都必须如此。
4. 上轮检查时特效仅有记录；本轮最新 `utils/match3.js` 已有特殊棋子生成、保留和扩展消除，WXML 也已有徽标。当前 `node scripts/test-match3.js` 为 **26 通过 / 0 失败**。这只证明现有测试覆盖的引擎行为，不能证明动画、学习、竞技或盈利完成。
5. 不采用「115% 最佳难度」「7 秒催产素」「12–15Hz θ波」等无可靠依据或错误的公式。

### 9.4 参考资料如何变成设计，而不是堆功能

King 官方文档中确有阶段竞技、团队协作及不同奖励结构 [R1–R3]；这证明机制存在，不证明复制后就能增长。建议本项目先实现「同盘挑战 + 个人最好成绩」，再根据真实回访决定是否加入小组周赛与协作目标，避免用户太少时做空榜。

动机研究支持胜任、自主、联结作为分析框架 [R4]。本项目对应：能理解自己为何赢、存在普通消除与制造特效的取舍、能与真实朋友比较同一局。签到和盲盒不能代替这些核心体验。

视觉指南要求可读、可操作、不以颜色独占传达信息 [R5–R6]，不是要求去掉所有颜色。候选方向为低干扰背景、清楚牌面、有限重点色；藏文形体为视觉中心，文化装饰在边缘与结算表达。具体触点和字号依目标设备实测，不把桌面截图等比例缩放当移动端验收。

音频指南支持分轨控制与突出重要语音 [R7–R9]。本项目不应再把「低 RMS / 循环无爆音」等同于好听，也不能把刺激等同于持续加响、加速、加震。音效负责操作和结果，音乐负责局内情绪，朗读负责学习；高潮有峰值，思考有留白。

### 9.5 眼睛、耳朵、手感、大脑、心情共用一份事件表

以下是待实施样板的设计契约，不是实测效果：

| 事件 | 视觉 | 声音 | 触感 | 决策与情绪作用 |
|---|---|---|---|---|
| 选中/拖动 | 原位明确高亮，合法目标可理解 | 轻短点击 | 可选极轻反馈 | 确认输入被接受，不抢戏 |
| 无效交换 | 回弹并解释原因，不靠弹窗堆提示 | 克制的回弹声 | 默认可不震 | 让玩家理解规则，避免羞辱 |
| 普通消除 | 字形和消除路径可辨 | 短结果声；挑选目标字读音 | 轻反馈 | 确认有效行动与学习对象 |
| 特效生成 | 棋子保留、图案清晰、规则可查看 | 独立生成音 | 与普通不同但不过强 | 让玩家预期未来收益 |
| 特效触发/多轮连锁 | 逐轮因果清晰、强度有上限 | 有层次、并发受控 | 关键轮次反馈，有冷却 | 从布局到爆发，保留控制感 |
| 听辨/词句学习 | 突出目标，减少无关动画 | 目标语音完整播放，音乐降低 | 不干扰听辨 | 把注意力交给音形/意义 |
| 胜利/失败 | 达标与差距真实、下一步明确 | 胜利收束；失败克制 | 可选收束反馈 | 成就可信，失败可复盘 |

统一事件最少包含 actionId、eventId、round、内容 ID、目标变化和棋盘变化。渲染、音频、触觉订阅同一事件；奖励只结算一次。视觉和声音同步须录屏检查；听辨任务有静音替代提示或明确说明，关闭震动不影响规则。

### 9.6 单字 → 词组组合 → 句子组合：现在预留契约，逐级实现

不预建庞大编辑器，先以一条完整链路证明扩展空间：
- 内容实体稳定 ID，区分字母/音节/词/短语/句子，包含藏文、读音来源、含义、先修项、已核验状态和版本。
- 字形匹配、听音选择、部件组字、词块组合、句序/语境选择是不同任务类型，不能都复用「两张文本相同」。
- 词与句引用组成内容 ID；允许多种正确答案或语境限定；合法附加字表继续沿用，不随机生成看似藏文的错误组合。
- 藏文 Unicode 组合与叠字按字形簇处理，不按 JS 字符数随意拆。tsheg/shad 排版规范继续有效。
- 短词用宽卡，句子用词块槽位与可换行区域；不以无限缩字或长按放大代替正常阅读。
- 掌握度按 contentId + skill 记录曝光、作答、提示、正确性、时间和下次复习；游戏积分与学习证据分开。
- 先做单字完整样板，同时用一个真实词组合和一个句序任务验证数据/排版/音频契约，后两者为扩展探针，不提前铺满课程。
- 学习验收含无颜色线索、未见过的布局、次日回忆；原始提取与间隔练习研究支持方法 [R10–R12]，不保证本产品具体提升比例。

### 9.7 分发与赚钱的可执行验证

H5 用于低门槛外链体验和素材试验，但它不会自动获得曝光，也不保证任意平台内都能顺畅打开。微信侧核实小游戏/小程序路线、资质、分享、广告与支付实际适用条件；抖音侧研究小游戏录屏与内容挂载 [R13–R14]，不能只复制微信分享卡。三端共同维护规则与内容版本，分别验证登录、存档、音频激活、录屏、支付和回流。

建议首要商业假设为「好玩的免费核心 + 自愿激励广告」，备选为不破坏竞技公平的装饰付费；学习内容/服务需在独立学习价值成立后验证。是否可上线依主体与后台条件决定，当前未验证。商业研究和接入可行性必须与样板同时开展，不能拖到最后才发现不能收款。

每条变现路线要明确受益、交付与结算。激励广告仅在玩家主动选择后尝试加载；无填充、取消、中途退出和完成分别处理，按可信回调发奖，防重复。不为制造看广告需求而故意制造不可解局。

经济模型以真实净结算口径记录：
- 广告收入 = 有效计费展示 / 1000 × 实际净 eCPM；不要把完成次数当所有广告形式统一计费口径。
- 付费净收入 = 实收 − 退款 − 实际平台/支付扣费；避免把已净结算金额再次扣分成。
- 贡献 = 净收入 − 获客与可变服务成本；利润还需扣固定内容制作与运营成本。
- 生命周期贡献与获客成本按同一渠道、同一用户群、同一观察窗计算；收入规模不代表盈利。
- 无数据只给低/中/高假设，标明样本、时间窗和来源，不编「必赚」「必病毒」结果。

增长看新增有效玩家与留存，竞争看挑战接受与复赛，商业看净收入和贡献，学习看延迟迁移。K 类传播系数需固定观察窗、按归因去重，不能用点击分享按钮的人数代替新增玩家。

### 9.8 给 WorkBuddy / DeepSeek 的实施顺序与验收门槛

1. **冻结并读取审查快照**：检查 git diff，不覆盖其他修改；复核 G01–P01 的最新状态。交付「证据 / 是否仍存在 / 修改位置 / 验收方法」表。
2. **完整单字样板**：真实胜负、可读目标与步数、特效、障碍、逐轮反馈、得分和读音。选少量有教学意图的关卡验证布局选择与失败复盘；不先扩至几百关。
3. **同批做声画候选**：同一玩法对比现版/简化布局，音频做随机顺序盲测，等响度与设备条件尽量一致；可先做约 12–20 人的探索性试玩（这是研究预算建议，不是统计有效性保证）。分别含普通消除玩家与藏文学习者。
4. **加入一条真实传播链、一条可用变现链**：同盘挑战与归因；实际可接平台先跑可选广告或支付交付。可用性、收益和用户体验分别记录，不把沙箱通过当盈利。
5. **扩展探针与跨端验收**：一个词组合、一个句子任务；H5/微信/抖音分别完成最小运行能力验证，再决定投入和发行顺序。
6. **放量门槛**：先记录现版基线，预先约定主指标与保护指标。主指标可选主动再来一局/次日有效回访；保护指标含读音辨认、烦躁评分、误触、性能和净贡献。一次试验只针对明确假设；小样本只用于定位问题，不能宣布显著提升。失败则修订或停止该路线。

必须交付：源代码差异、测试输出、目标设备录屏、每个变现/分享关键状态的真实记录、匿名试玩观察、指标口径和结果。所有建议参数标注为初值；没有真实玩家和结算数据，不得声称已达到「有人玩、能赚钱」。

### 11.3 新抓到的具体问题：不能再以「自检全绿」关闭

**F01 / P0：微信学习线真实点选会报错。**

game.js 的 onTapTile 只定义 idx 和 first，配对分支调用 `handleMatch(first, second)` / `handleMismatch(first, second)`；second 未定义。本轮在 Node VM 读取真实 Page 定义，替换平台、音频和存储接口，不替换 onTapTile：两次选中同 ID 的牌，复现 `ReferenceError: second is not defined`。该探针未修改工作区文件。

**F02 / P0产品：限步目标缺乏实际压力。**

当前 objectiveFor 统一取约总牌数 60% 为消除目标，再给 `ceil(target/3*1.6)+3` 步；非法交换不扣 m3left。以每个有效动作至少净消 3 张为前提，只要盘面持续可走，就在 `ceil(target/3)` 步内达标，早于预算。因此当前步数耗尽路径难以由正常有效操作触发；若无步可走，表现为死局而非可理解的策略失败。

| 关卡 | 目标 | 步数预算 | 按每步净消 3 张的达标步数上界 |
|---|---:|---:|---:|
| 1 | 18 | 13 | 6 |
| 2–4 | 24 | 16 | 8 |
| 5 | 30 | 19 | 10 |
| 6–10 | 36 | 23 | 12 |

这是根据当前规则的条件推导和配置计算，不是玩家胜率统计。不能简单把预算砍半后宣布好玩；需增加目标差异、布局取舍和可复盘的失败，做代表性局面对照。新手教学局可宽松，后续挑战局不能全沿用该公式。

**F03 / P1：首次有效游玩埋点读旧值。**

成功交换后先判断 `this.m3cleared > 0`，之后才写入 res.spent。读取真实 Page 方法的探针结果：第 2 关固定 seed=12，首个合法交换 [0,1] 净消 6 张，attempts=1，但 chplay 事件列表为空。首步即达标或只玩一步退出时会遗漏；后续才触发也不能称首次动作记录正确。

验收：首个成功动作恰好记录一次；非法动作不记；同挑战再次打开去重；不能以事件名字符串存在判断通过。tracker 使用事件值真值判断的去重也需覆盖相对时间 0 秒这一边界。

**F04 / P1：胜负只修了进度入口，结算表现与奖励未整体对齐。**

结果页已经 `if(won) completeLevel`，这是实质修复，不再误报为「完全未分胜负」。但 game.finishLevel 仍统一 audio.win / celebrate；结果页在 won=0 时仍进入成绩、星数、印章和碎片逻辑。失败应发哪些参与奖励可另定，但必须明确区分达标奖励、参与奖励与学习掌握，不能意外走到成功路径。结果页当前仍将 pairs/attempts 用作正确率；三消下张数/动作数不是学习正确率，可能超过 100%。

**F05 / P1：逐轮播放只显示落定快照，尚未形成完整反馈过程。**

当前每 260ms 展示一次 cellsAfter，没有完整展示交换轨迹、消除前命中、破碎与补入路径。该定时链未见与页面卸载绑定的统一取消；afterPlay 先解锁，最终落地动画可能仍未完成。此为源码风险，未宣称已在真机复现。验收需录屏并覆盖中途返回、切后台、重进和快速输入；不能把读取了 rounds 当作反馈闭环完成。
