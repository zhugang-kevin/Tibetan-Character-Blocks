# 藏文 TTS 服务商评估（D67）

> 起因（用户原话，2026-10-10）：「我发现你给我的很多信息都是太官方的，
> 所以你还是真正忽略了市场上其他的相关更好的服务商……天翼的质量并不是很好的，
> 但是你强烈推荐我使用后，我们才发现有那么多的问题。为什么会出现那么多的错误，
> 这个需要完美的解决方案。」
>
> **本文档的结论：错的不是"选了一个不好的服务商"，而是"我没有任何选型验收机制"。**

---

## 一、先认账：我当时错在哪

我把天翼（TeleAI / `aipaas`）当成**"唯一能出声的方案"**直接推荐，
理由是"它能输出藏文音频"。这是**把"能出声"当成了"质量合格"**。

后果是我把整条音频管线都押在它上面 —— 清单生成、UI 播报、体检门禁 ——
然后才逐条撞上问题：

| 时间 | 撞上的问题 | 暴露时机 |
|---|---|---|
| D56 | 16 种文本写法全部失败（0 字节 / 30ms 静音桩） | 上线前 |
| D57 | **9/36 个元素根本没有音频**（覆盖率仅 75%） | 用户反馈 |
| D58 | `ཨོཾ` 的**鼻音符号不被发音**（去掉 ཾ 时长完全不变） | 我自己测出来的 |
| D58 | 六字真言也是中文 Edge TTS 念汉字，**根本不是藏语** | 代码审计 |
| D59 | 8 条字母用了 `ཱ` 才合成出来 → 念成 **长 "kaa"**，与标准短 a 不同 | 排查才发现 |

**根因不是运气不好，是选型时没有验收标准。** 我当时没有问：
「覆盖率多少？」「它认不认鼻音符号？」「它区分长短元音吗？」——
这三个问题每一个都能**机械检测**，而且事后全都证实了缺陷。

## 三、根本解法：把"选服务商"变成一道**有验收标准的门禁**

不能再靠"我觉得这个行"。**任何服务商想当默认，必须先通过机械验收。**

### 1. 三条探针（这三条各自都对应一个真实踩过的坑）

| 探针 | 检测什么 | 机械判据 | 能抓出 |
|---|---|---|---|
| **P1 覆盖率** | 每个待合成条目是否都有可听输出 | 产出率 = 有声条目 / 需求条目，必须 **100%** | 天翼 9/36 缺失 |
| **P2 变音符号敏感度** | 去掉鼻音/元音符号后，输出**是否变化** | `T(ཨོཾ)` 与 `T(ཨོ)` 的时长或波形差异必须 > 阈值 | `ཨོཾ` 鼻音丢失 |
| **P3 长短元音区分** | `T(ཀ)` 与 `T(ཀཱ)` 是否被区别对待 | `T(ཀཱ)` 时长须 ≥ `T(ཀ)` × **1.15** | 8 条字母念成长 "kaa" |

**P2/P3 是关键**：它们不需要人耳就能判定"这个符号有没有被发音"。
天翼的三个缺陷，**三条探针全部能自动抓到**。

### 2. 服务商可插拔（不再锁定）

新增 `scripts/tts_bakeoff.py`：一份**注册表** + 一套**统一探针**。
接入新服务商只需实现 `synthesize(text, rate) -> wav bytes`，
游戏代码、UI、清单**一行都不用改**。

```
scripts/tts_bakeoff.py --provider luel      # 试一家
scripts/tts_bakeoff.py --all                # 全跑一遍，出对比报告
```

### 3. 真人录音永远优先

清单里 `form: 'recorded'` 的条目**不受服务商影响**，
真人录音一旦就位就永久覆盖 TTS —— 避免"换服务商把已修好的音频又换掉"。

## 五、复盘教训（写进 D67）

> **我犯的不是"选错了服务商"，是"没有验收标准所以选了谁都一样"。**
>
> 这次的教训和之前那些假绿门禁是**同一个家族**：
> 我当时只看"有没有输出"，不看"输出对不对"——
> 和 `existsSync` 只看文件在不在、`indexOf` 只看调用在不在，**完全同构**。
>
> 凡是"能跑通"的检查，都要补一条"**跑得对吗**"的检查。

## 六、验收实测结果（2026-10-10，`scripts/tts_bakeoff.py`）

| 探针 | 天翼 TeleAI 实测 | 判据 | 结论 |
|---|---|---|---|
| **P1 覆盖率** | **60%**（36 条缺 10 条） | 100% | ❌ 不通过 |
| **P2 变音符号敏感** | `ཨོཾ` vs `ཨོ` 时长差 **+0.0%** | ≥8% | ❌ **鼻音/元音符号根本没发音** |
| **P3 长短元音区分** | 裸 `ཀ` 本身**不可闻**，无从比较 | 两侧均可闻且比值 ≥1.15 | ❌ **合成不出孤立辅音** |
| **总判** | | 三项全过 | **不合格** |

### 一个必须说明的口径差异

- **P1 冷测 60%**：单次合成、不做任何文本变体尝试、不重试 —— 也就是**新接入一家服务商的真实初次成功率**。
- **D57 记录的 75%**：已经把 16 种文本写法、重试、参数扫描全用上之后才达到的**最好情况**。

也就是说：当天翼是**唯一**能出声的选项时，我实际是靠"把 16 种写法全试一遍"才把覆盖率从 60% 抬到 75% —— 而剩下 25% 无论怎么试都发不出来（D56 已证）。**这个细节当时完全没有向用户说明。**

### 探针本身的两个自测缺陷（已修，值得记）

1. **P3 第一版是假通过**：`ཀཱ / ཀ` 算出来 **22.99**，远超 1.15 的门槛 → 判"通过"。
   但真相是**裸 `ཀ` 几乎没合成出来**，分母趋近 0 把比值抬上了天。
   **比值大 ≠ 区分得好**，也可能只是分母坏了。修正为「两侧都必须先可闻」。
2. **评测集加载方式错了**：第一版用 Python 的 `exec()` 去执行 `voices.js` ——
   那是 **JavaScript**，直接语法报错。教训：与今晚其余 bug 同源，
   **假设文件格式 = 不验证文件格式**。改为用 node 导出 JSON 再读。

这两条都是**探针自己**的缺陷 —— 如果我不把探针也当成"需要被证伪的对象"，
它就会变成新的"看起来很正式的假数字"。
