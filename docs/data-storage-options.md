# 数据存储：选型与结论（D92）

> 用户问：「关于数据，不是很确定我们是否有**免费的最好选择**。」
>
> **直接回答：有，但要看是哪一类数据 —— 本项目的数据天然分成两半，两边的最优解不同。**
> 混为一谈会选错：把服务端数据放到客户端方案上，或反过来。

---

## 一、先把数据分成两半（这是关键）

| | **甲类：用户自己的数据** | **乙类：支付与跨用户数据** |
|---|---|---|
| 例子 | 学习进度、收藏的文化卡、灯火数 | **支付订单**、B 送礼给 A 的记录 |
| 谁读写 | **小程序端**（用户自己） | **服务端**（后端进程） |
| 隔离要求 | 每人只能读写自己的 | 服务端持有凭证，跨用户 |
| **最优解** | ✅ **WorkBuddy 云服务**（已开通） | ✅ **服务端 SQLite**（已落地） |

**为什么必须分开**：官方的虚拟支付红线是「**签名只能在服务端计算**」，
而微信发货回调也是打到**服务端**的 —— 所以**订单必须住服务端**。
反过来，托管云方案的模型是「App 端 + RLS 按用户隔离」，它**做不了**「B 写 A 的数据」
（RLS 的 INSERT 策略会直接拒绝伪造的 owner）。

---

## 二、甲类：用户数据 → **WorkBuddy 云服务**（免费）

**已开通并建表**（本轮）：

| 项 | 值 |
|---|---|
| 应用 ID | `wbapp_k5GNOD13SCij3w7Ki5cYlc` |
| 形态 | `miniprogram`（按本项目指定） |
| 计费状态 | `normal` · 供给状态 `assigned` |
| 已建表 | `progress`（owner_id / done_stages / lamps / cards / updated_at） |
| 安全 | **RLS 已开启**，策略 `progress_own`：`owner_id = auth.uid()` 才能读写 |

**它为什么是「免费的最好选择」**：

| 维度 | 说明 |
|---|---|
| **免费** | 随 WorkBuddy 提供，无需单独购买数据库或服务器 |
| **免运维** | 不买服务器、不配数据库、不管备份 |
| **隔离有保障** | RLS 在**数据库层**保证「每人只能碰自己的行」—— 不靠前端自觉 |
| **零额外服务商** | 符合「最小化服务方」偏好：不引入第三家 |
| **可迁移** | 底层是 PostgreSQL + PostgREST，结构化数据随时可导出 |

**它解决的真实问题**：现在学习进度、收藏、灯火数只存在**本地 storage**，
**换手机就全丢**。云端备份后跨设备可同步。

---

## 三、乙类：支付订单 → **服务端 SQLite**（同样免费）

**已落地**（`server/store.js`）：把原来的**内存 `Map`** 换成 SQLite。

**为什么是「免费的最好选择」**：

| 维度 | 说明 |
|---|---|
| **免费** | `node:sqlite` 是 **Node 内置**（22.5+），**不用装任何包** |
| **ACID** | 支付数据必须要事务 —— 这一点上 SQLite 与 Postgres 同级 |
| **零锁定** | 数据就是**一个文件**，随时可导出/搬迁，不存在「数据人质」 |
| **零额外服务商** | 不新增账号、不新增账单 |
| **量级匹配** | 一个小程序的订单量，远在 SQLite 的舒适区内 |

**已验证（不是推测）**：
- 写入→读回 ✓ ／ 重复订单号被**主键**拒绝 ✓
- `claimDelivery()` 首次 true、重推 false —— **防重复发货** ✓
- session_key 覆盖更新 ✓ ／ 兜底查单能找到「已支付未发货」✓
- **重启后数据仍在** ✓（这正是本轮要修的：旧版内存 Map 在这里就丢）

**⚠️ 两个已知前提（如实标注）**：
1. `node:sqlite` 在 Node 22 仍是**实验特性**（会打 ExperimentalWarning）；
   若部署环境 Node < 22.5，改用 `better-sqlite3`（同样单文件，API 几乎一致）。
2. 单文件存储适合**单实例**部署。若将来要多实例横向扩展，再换 Postgres —— 届时数据可平滑迁出。

---

## 四、一句话结论

> **免费的最好选择是「两套并存」，而且两边都是免费的：**
> · **用户数据 → WorkBuddy 云服务**（已开通，免运维，RLS 隔离）
> · **支付订单 → 服务端 SQLite**（Node 内置，ACID，单文件零锁定）
>
> **不是「二选一」，而是「各归其位」** —— 硬要合一，要么违背官方红线，要么违背 RLS 模型。
