# 🎯 DeepSeek 在 WorkBuddy 中的完整工作指南

## 第一部分：这个项目是什么？（5分钟了解）

### 最简单的解释

你现在要维护的是一个**手机小游戏**。

**用户玩这个游戏做什么？**
- 玩一个简单的配对消除游戏（点两个相同的方块就消失）
- 同时学习藏文字母（有30个字母要学）
- 每玩完一关，就能看到一座藏族寺庙的图片
- 150关全部玩完，就集齐了150座寺庙

**这个游戏在哪里玩？**
- 微信里面（像你用微信一样）
- 也可以在网页上玩（用浏览器）

### 这个项目现在有什么问题？

**问题清单（只有这些）：**

| 序号 | 问题 | 现状 | 优先级 |
|-----|------|------|--------|
| 1 | **游戏一玩就停止** | 玩一会儿没反应了 | 🔴 最紧急 |
| 2 | **会报一大堆错误** | 屏幕显示红色错误信息 | 🔴 最紧急 |
| 3 | **150座寺庙还没有真实图片** | 只有10张风景图，缺140张 | 🟡 重要 |
| 4 | **没有自动续跑** | 一个对话结束就停了，不会自动继续工作 | 🔴 关键 |
| 5 | **会碰其他文件夹** | 系统会改动其他项目文件，太危险 | 🔴 生命线 |

**最危险的问题：第5个** 
- 如果系统改坏了其他文件夹，会造成灾难性后果
- **绝对必须限制系统只能在"藏趣游戏"这个文件夹内工作**

## 第二部分：DeepSeek 的工作流程（这是你要教它的）

### 🚫 第一条铁律：不能停，不能报告，不能问

**记住这一句话：**
```
❌ 不允许：停止、等待反馈、报告问题
✅ 必须做：持续工作、自动修复、循环验证
```

**具体意思是：**
- ❌ 不能说"我找到3个问题，等你确认怎么修"
- ✅ 必须做"我找到问题 → 自动修复 → 检验是否成功 → 继续工作"
- ❌ 不能说"需要10分钟休息"
- ✅ 必须做"不停工作，直到所有问题都解决"

---

### 工作流程（5个步骤，循环执行）

#### 📍 第1步：**寻找问题**（15分钟）
**DeepSeek应该做什么：**
```
1. 检查整个项目的文件
2. 运行所有质量检查脚本
3. 看是否有错误或警告
4. 列出找到的所有问题
```

**检查清单（具体要检查什么）：**
- ✅ 所有150个关卡数据是否完整
- ✅ 所有代码文件是否有语法错误
- ✅ 游戏规则是否正确（配对、消除、计分）
- ✅ 所有图片文件是否存在
- ✅ 所有藏文字母是否正确
- ✅ 服务器配置是否安全
- ✅ 虚拟支付是否配置正确
- ✅ 所有测试是否通过

**怎么判断第1步成功了？**
```
如果能列出所有问题（可以是0个，也可以是100个），就算成功了
```

---

#### 🔧 第2步：**诊断问题根因**（15分钟）
**DeepSeek应该做什么：**
```
对于第1步找到的每一个问题，要回答：
1. 这是什么问题？
2. 为什么会发生？
3. 怎么才能完全解决？
```

**诊断清单（问自己）：**
- 这个问题是代码错误吗？
- 还是数据缺少什么？
- 还是配置不对？
- 还是文件损坏了？

**怎么判断第2步成功了？**
```
能清楚说出"这个问题的根本原因是XXX"
```

---

#### 🛠️ 第3步：**自动修复**（不固定时间）
**DeepSeek应该做什么：**
```
对于每一个诊断出的问题，直接修复代码
不要问，不要等，直接改！
```

**修复的规则（必须遵守）：**
1. ✅ **只改项目文件夹内的文件**
   ```
   允许改：I:\藏趣游戏\pages\*.js
   允许改：I:\藏趣游戏\data\*.js
   允许改：I:\藏趣游戏\utils\*.js
   ❌ 禁止改：C:\Windows\*
   ❌ 禁止改：其他项目文件夹
   ```

2. ✅ **改完一个文件就立刻验证**
   ```
   修改 → 保存 → 运行测试 → 检查是否成功
   ```

3. ✅ **要记录改了什么**
   ```
   记录格式：
   - 文件名：pages/game/game.js
   - 改动内容：修复了配对消除的计分逻辑
   - 为什么改：因为连击计分有Bug
   - 结果：测试通过 ✓
   ```

4. ✅ **改完所有相关文件才能继续**
   ```
   不能改一半，必须把相关的都改完
   比如改了游戏规则，就要同时改测试文件
   ```

**怎么判断第3步成功了？**
```
所有被改的代码都经过测试，没有新的错误出现
```

---

#### ✅ 第4步：**验证修复**（10分钟）
**DeepSeek应该做什么：**
```
对于刚才修复的每一个问题，要证明它确实被修复了
```

**验证清单（具体怎么验证）：**

对于**游戏逻辑**问题：
```
1. 运行：node scripts/test-all-150.js
2. 看结果：应该显示"150/150 通过"

```

对于**代码质量**问题：
```
1. 运行：node scripts/validate.js
2. 看结果：应该显示"0 个错误"
3. 如果有错误，修复没成功
```

对于**游戏行为**问题：
```
1. 运行：node scripts/test-page-behaviour.js
2. 看结果：应该显示"66/0 通过"（数字可能不同，但最后是/0）
3. 如果是其他结果，修复没成功
```

对于**服务器安全**问题：
```
1. 运行：node scripts/test-server-hardening.js
2. 看结果：应该显示"18/0 通过"
3. 如果不是，修复没成功
```

**怎么判断第4步成功了？**
```
所有验证都显示"通过"，没有任何"失败"的标记
```

---

#### 🔄 第5步：**循环回到第1步**
**DeepSeek应该做什么：**
```
回到第1步，重新检查整个项目
看是否有新的问题出现
```

**什么时候可以停止循环？**
```
✅ 只有这种情况可以停止：
1. 第1步找不到任何问题（0个错误）
2. 所有质量检查都通过
3. 所有150个关卡都能正常玩
4. 游戏不会无故停止或报错
5. 所有自动化测试都是绿色（通过）

❌ 这些情况不能停止：
- 还有问题没修
- 测试显示红色或黄色
- 有任何错误警告
- 自己觉得"可能已经够好了"
```

## 第四部分：工作周期与自动化（这是核心）

### ⏱️ 标准工作周期

**一个完整的工作周期 = 10-15分钟**

```
第1步：寻找问题      (5分钟)
  ↓
第2步：诊断根因      (3分钟)
  ↓
第3步：自动修复      (4分钟)
  ↓
第4步：验证修复      (2分钟)
  ↓
第5步：循环检查      (1分钟)
  ↓
回到第1步或停止
```

### 📍 关键时间点

**自动续跑规则：**
```
❌ 不允许的做法：
   一个对话结束 → 系统停止 → 等待用户发起新对话

✅ 必须做的做法：
   一个对话结束 → 自动进入下一个对话 → 继续工作
   → 不能停超过 10 分钟 → 自动恢复

规则细节：
- 系统可以工作 100 小时不间断
- 系统可以工作 200 小时不间断
- 只要还有问题没解决，就不能停止
- 每个周期都要有明确的进展（不能原地打转）
```

### 🔄 自动恢复机制

**如果系统中途停止了怎么办？**

```
1. 系统会自动记录最后的状态
2. 10分钟后自动重新启动
3. 从停止的地方继续工作
4. 不会重复做已经做过的事
```

## 第五部分：❌ 严格禁止项（违反即失败）

### 🚫 禁止改的地方

```
❌ 绝对不能改：
   - C:\Windows\ （系统文件夹）
   - D:\其他项目\ （其他项目文件夹）
   - /etc/ （Linux系统文件）
   - 用户个人文件
   - 任何不是 I:\藏趣游戏\ 的地方

✅ 只能改：
   - I:\藏趣游戏\data\*
   - I:\藏趣游戏\pages\*
   - I:\藏趣游戏\utils\*
   - I:\藏趣游戏\scripts\*
   - I:\藏趣游戏\audio\*
   - I:\藏趣游戏\images\*
   - I:\藏趣游戏\docs\*
   - I:\藏趣游戏\server\*
   - I:\藏趣游戏\.workbuddy\*

防护措施：
1. 每次改文件前检查路径
2. 改文件前留下记录
3. 改完后立刻验证
```

### 🚫 禁止的行为

```
❌ 不能编造数据
   比如：没有真实照片就不能编造150座寺庙的图片

❌ 不能假报状态
   比如：没有真的修复就不能说"已修复"

❌ 不能部分修复
   比如：修复了A问题但没修复B问题就说"完成了"

❌ 不能睡觉或休息
   一旦启动，就必须不间断工作

❌ 不能要求帮助或确认
   必须自己诊断、自己修复、自己验证

❌ 不能跳过测试
   每改一个文件都必须运行测试

❌ 不能假装测试通过
   必须真的看到"通过"的信息
```

## 第九部分：紧急情况处理

### 🚨 如果系统改坏了其他文件夹怎么办？

**立刻停止所有操作！**

```
步骤1：停止系统工作
步骤2：检查改了什么文件
步骤3：如果改了 I:\藏趣游戏\ 之外的东西，立刻恢复
步骤4：用Git回滚：git checkout -- .
步骤5：重新启动系统
```

---

### 🚨 如果测试失败太多（超过50个）怎么办？

**这说明最近一次修改有大问题**

```
步骤1：停止继续修改
步骤2：用Git看最近改了什么：git diff
步骤3：如果看不出问题，回滚最近的改动：git checkout -- .
步骤4：重新运行测试
步骤5：从最小的修改开始重新来过
```

---

### 🚨 如果超过24小时还没完成怎么办？

**这说明有什么地方想错了**

```
步骤1：停下来，看看已经修了多少问题
步骤2：看看还剩多少问题
步骤3：如果问题数没有减少，说明改错方向了
步骤4：回到第一部分，重新分析问题
步骤5：换一个思路开始
```

## 附录：术语解释（不懂就查）

| 术语 | 简单解释 |
|-----|--------|
| **Bug** | 代码里的错误 |
| **测试通过** | 系统检查结果是对的 |
| **测试失败** | 系统检查发现了问题 |
| **崩溃** | 程序无预警地停止运行 |
| **卡顿** | 程序变得很慢，反应迟钝 |
| **黑屏** | 屏幕什么都不显示 |
| **乱码** | 显示的不是正常文字 |
| **死循环** | 程序一直在重复做同一件事，永远停不下来 |
| **内存泄漏** | 程序用过的内存没有释放，最后内存满了 |
| **回滚** | 把改动恢复到之前的状态 |
| **Git** | 用来追踪文件改动的工具 |
| **命令行** | 黑色窗口，用来输入命令 |
| **语法错误** | 代码写错了，程序看不懂 |
| **运行时错误** | 程序开始运行了才发现的错误 |
| **幂等** | 做一遍和做多遍结果一样 |
| **原子操作** | 要么全部成功，要么全部失败，不会做到一半 |
| **沙箱** | 一个被隔离的环境，里面的改动不会影响外面 |
| **部署** | 把程序放到服务器上给用户用 |
| **回调** | 一个函数在某个条件满足时被自动调用 |
| **异步** | 不用等前面的任务完成，可以同时做多件事 |
