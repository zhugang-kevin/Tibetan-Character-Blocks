    · 裸字形：19/30 静音或过短（peak <1000，实测多为 20~70，即噪声底）
    · 加 ཱ 后：**另一个** 19/30 静音 —— 两套失败名单**不重合**
      （ཟ/ལ/ཧ/ཨ 裸的有声、加 ཱ 反而没声；ར/ཤ/ཚ/ཕ/ཛ 反过来）
    · 即：**没有可预测的规则**，取两者较好者仍有约 1/3 字母发不出声。

## D63 / D63.1 —— 「假绿门禁」审计（本项目最该记住的一轮）
用户第 5 条反馈：「系统会制造假象，原本所有流程都显示全绿，但红色/黄色的问题也显示绿色」。

**① harness 自己先被证伪了一次（必须记）**：第一版写在 **Node** 里，跑出「22/22 抓到，
检出率 100%」。但同一刻 `node scripts/validate.js` 单独跑是 exit 0 全绿。真相：

② **CAUGHT/MISSED/INJECT_ERROR/RUNNER_ERROR 四分**，变异没注入成功绝不算结论。

## D64 —— 设备响应式（用户第三次强调：我一直忽略的大问题）
用户口径（务必记住的优先级）：**手机（所有型号）→ 平板（所有型号）→ 电脑（最后）**。

**① 先把优先级写进代码**：新增 `scripts/audit_device.py` —— 把 play.html 注入探针后用
headless Chrome **按目标尺寸真实加载**，机械量三件事：横向溢出 / 过小字号 / 过小点击区。
设备矩阵：手机 320·360·375·390·414·430 → 平板 768·810·1024 → 电脑 1280。
（踩坑三连：① 探针一开始放在外层 iframe 里 → 量的是壳子不是游戏，必须注入 play.html 自身；
② 结果塞 <title> 走 JSON → 被 HTML 转义成 &quot; 且截断，改成只回传一行 ASCII 摘要；
③ `a + b % args` 里 % 只作用于 b，报错信息会误导成「设备问题」。）

**② 找到了一个此前完全没人看的事实**：小程序是 **rpx 体系**（750rpx = 屏宽），
**字号按屏宽等比缩放**。于是「在我这台机器上正常」根本推不出「用户机型上正常」。
按 320pt 折算：22rpx=**9.4pt**、24rpx=10.2pt、26rpx=11.1pt —— 而当初所有字号都是按
**375×667 一台机器**定的（375 上 22rpx=11.0pt 刚好及格）。统计：**WXSS 60 处 < 24rpx**
（320pt 上读不清）、**体验版 29 处 < 11px**（px 不随屏宽缩放，**所有**机型都偏小）。
**这不是「某个机型坏了」，是整套字号体系在小屏机型上系统性偏小。**

**③ 处置**：`scripts/fix_type_scale.py` 抬下限（WXSS ≥24rpx / H5 ≥11px），改 60+29 处，
**改完回读校验**、不足数 exit 1。复测：**10 个尺寸全清**（溢出 0 / 小字号 0 / 小点击区 0）
—— 证明放大字号**没有撑破布局**（是量出来的，不是推测）。
**门禁 §54（6 项）**：矩阵在册且手机≥4/平板≥2/电脑≥1 档、WXSS 无 <24rpx、
H5 无 <11px、**WXSS 不得写死 ≥100px 宽度**、24~26rpx 区间**报警告**（320pt 仍 <11pt，
如实分级不粉饰）。

shell 吃掉变成 `s`，**匹配不到任何东西却报告「改了 0 处」** —— 我差点据此宣称「已修复」。
与 D63 的假绿同源：**「没报错」≠「真的做了」**。改成脚本落盘 + **回读校验**才作数。

**⑤ 诚实留档的缺口**：320pt 仍是边缘档（24rpx=10.2pt 勉强可读，要 ≥11pt 需全面抬到
26rpx = 全局视觉变更，需真机目视配套，不能盲改）；只覆盖横向溢出，**纵向溢出与安全区
（刘海/底部横条）未核验**；平板只做到「不破版」，**没做「用好平板」**（仍是手机版式）；
探针量的是 **H5**，小程序端 WXSS 实际渲染**必须真机复核**（rpx 折算是公式算的）。
