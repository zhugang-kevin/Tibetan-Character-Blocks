## D73 —— 拿到可信的字体度量（三次测量里第一次可信）；并修掉整条链上的 4 个坑
用户要求按顺序执行：修验证脚本 → 确认字体真在渲染 → 重跑 make_logo → 重测字宽 → 视觉重心。

**① 建成 `scripts/measure_font_metrics.py`，自带两条自证**（这是关键，不是可选项）：
- **对照实验**：同一字符渲染两次 —— 目标字体 vs **必然不存在的字体名**。
  两者墨迹相同 ⇒ 目标字体没生效 ⇒ **当场判定「测量作废」**。
- **字形差异**：不同字母的**墨迹像素数**必须互不相同（**不能**用宽度判断 ——
  这是我 D72 犯的错；实测 Noto 的基字宽度其实各不相同：ཀ .748 / ཁ .723 / ག .762 / ང .617）。

**② 一连修掉 4 个坑（每个都会静默给出错误结果）**：
1. **字体被截断**：第一次下到 796,480 字节，但 TTF 表结构要求 **2,063,502 字节**
   （`gvar` 表末端）→ Chrome 报 `TT/error`。**用逐表偏移校验才发现**（不能只看文件大小）。
   重下得 **2,063,504 字节、0 个越界表**。
2. **headless shell 不够用**：`chrome-headless-shell`（精简版）对大字体报 NetworkError 并
   **静默回退**；改用完整版 `chromium-1228` 才加载成功。
3. **@font-face 的两种引用方式都不可靠**：base64 data URL（1MB+）与 `file://` 都失败；
   **正解是起本地 HTTP 服务器**（页面与字体同源）。
4. **不要押在 `document.fonts.load` 的 promise 上**：它在大字体上报 NetworkError；
   改为「等它 + 超时兜底」双路。

**③ 真实度量（第一次可信）**：
```

tsheg / 基字 = 0.3797
```
**对比我此前"实测"的（回退字体）：0.426 / 0.158 / 0.371** ——
**比值碰巧接近，绝对 em 全错（基字小了 43%）。**
→ `grid.js` 的 tsheg 系数从 0.158 修正为 **0.284**，并把这次沿革完整写进注释。

## D74 —— 墨迹公式 / 重跑 make_logo / 视觉重心：三步的实际结果是「两步成、一步卡住」
**① 墨迹公式：换掉了整条技术路线。**

与 `measureText` 给的 `asc=42/desc=49` **明显矛盾**。与其继续猜画布状态，

结果 **ཀ 与 ག 恰好都是 141** → 误判豆腐块。**不同字形完全可能共享同一墨高**。

## D75 —— 墨迹测量成功（PNG 逐像素法）；且结论与假设**方向相反**
